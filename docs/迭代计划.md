### 迭代方向详情

#### 方向 1：模式切换（plan / build / target）

- **已有**：`plan mode` = `read_only` 权限模式，只允许 INFORMATION_TOOLS
- **缺陷**：
  - plan mode 不改变 agent behavior，只是限制了 tool 执行
  - 无 build mode（全力执行）和 target mode（专注特定目标）
  - CLI 完全不支持模式切换
- **建议迭代**：
  - [ ] 定义三种模式语义：`plan`（思考+规划，禁副作用工具）、`build`（全力执行）、`target`（限定目标范围的执行）
  - [ ] system prompt 根据模式注入不同的行为指引
  - [ ] CLI 增加 `--mode plan|build|target` flag + 运行时 `/mode` 命令
  - [ ] 模式持久化到 session metadata

#### 方向 2：权限设计

- **已有**：4 层防护（OS sandbox → 路径守卫 → 工具分类 → session permission mode），1500+ 行
- **缺陷**：
  - 复杂度高，4 层权限叠加难以推理
  - `full-access` 模式绕过所有 sandbox
  - 子 agent 没有 approval forwarding（子 agent 无法向用户请求批准敏感操作）
- **建议迭代**：
  - [ ] 简化/合并冗余的权限层
  - [ ] 子 agent approval forwarding 机制
  - [ ] 用户可配置的默认权限模板

#### 方向 3：上下文压缩

- **已有**：`session-compactor.ts`（689 行）双策略自动选择 + thinking level 控制 + fresh compact
- **缺陷**：
  - 复杂度高，多 provider 多 code path
  - fresh compact 只对桥接 session 每日执行，普通 session 无按需 compact
  - 无预算控制的跨 session 自适应压缩
- **建议迭代**：
  - [ ] 简化 compaction 策略选择逻辑
  - [ ] 普通 session 按需 compact（`/compact` 命令或自动触发）
  - [ ] 全局 token 预算管理

#### 方向 4：子 agent

- **已有**：`subagent-tool.ts`（959 行）+ run store + thread store + 权限继承，生产级
- **缺陷**：
  - 无 approval forwarding（子 agent 需要用户确认时无法传递请求）
  - 无结构化 hub 路由（子 agent 创建/发现的中心化路由）
  - 无并行 fan-out 模式
- **建议迭代**：
  - [ ] approval forwarding 机制
  - [ ] 并行子 agent 执行（`Promise.all` 模式）
  - [ ] 子 agent 结果合并/冲突解决

#### 方向 5：只聊天 CLI

- **已有**：`cli/chat.ts`（338 行）+ client + local-server，完整的流式 TUI
- **缺陷**：
  - 无 `--mode` plan/build flag
  - 无 diff 显示（文件变更摘要）
  - 无 `/fix`、`/explain` 等推理命令
  - 无行内文件编辑审批流程
- **建议迭代**：
  - [ ] 模式切换 CLI 支持
  - [ ] 文件变更 diff 展示
  - [ ] `/fix` `/explain` 等快捷命令
  - [ ] 工具执行确认流程（类似 Codex CLI 的 sandboxed 审批）

#### 方向 6：自检纠错复审

- **已有**：无。仅 `agent.ts:1324` 一行 prompt 指引
- **需要新建**：
  - [ ] 工具执行结果校验层（validate tool output before returning to LLM）
  - [ ] 失败自动重试机制（渐进式 fallback：重试→简化→替代方案）
  - [ ] 复审流程（agent 生成的代码/文件变更自动 review）
  - [ ] 自检 prompt 注入（"检查你的输出是否合理"结构化的 self-check loop）

#### 方向 7：自学习自进化

> 参考 Hermes Agent 三层学习闭环架构：
> ```
> 执行任务 → 反思 → 写技能 → 下次复用
>   ↕                    ↕
> Curator 后台整理    技能自改进（用一次修一次）
>   ↕
> Self-Evolution（GEPA）→ 读取执行轨迹 → 变异 → 评测 → PR
> ```

- **已有**：
  - `lib/skills/` — Skill 元数据解析框架（目录结构、schema 校验）
  - `lib/memory/fact-store.ts` — SQLite 事实存储（被动记录用户偏好）
  - `lib/experiments/registry.ts` — 实验框架（A/B 测试基础）
  - `lib/tools/` — 完整的工具系统（可被 skill 引用）
  - `core/session-compactor.ts` — 执行轨迹压缩（可作分析输入）
- **缺的**：反思阶段 → 技能自动创建 → Curator 管理 → GEPA 进化闭环

##### 7a. Skill 自动创建（一期，借鉴 Hermes）

目标：复杂任务后自动生成可复用的 SKILL.md

- [ ] 任务完成钩子（`task-complete` hook）：检测复杂任务（5+ 工具调用 / 跨多文件修改）
- [ ] 反思阶段 prompt：让 agent 总结"解决这类问题的最佳步骤/工具/教训"
- [ ] SKILL.md 自动生成器：写文件到 `~/.satori/skills/<name>/SKILL.md`
- [ ] 渐进式技能加载：Level 0 只加载名称摘要（~20 token），Level 1 全文，Level 2 引用文件内容
- [ ] 技能触发匹配：根据用户 query 语义匹配已有技能，自动注入 system prompt
- [ ] 技能执行中自改进：agent 使用 skill 时可以标注"这条需要更新"，任务结束时自动 patch

##### 7b. 执行轨迹分析（基础数据层）

目标：记录 agent 每次执行的全链路数据，供后续分析和进化

- [ ] 轨迹记录器：执行日志结构化（tool call + input + output + 成功/失败 + token 消耗）
- [ ] 失败模式分类：编译错误、测试失败、权限拒绝、超时、LLM 幻觉等
- [ ] 用户反馈收集：隐式（接受/拒绝 diff、修改 agent 输出）+ 显式（点赞/点踩 /rating 命令）
- [ ] 偏好向量化：将用户偏好（语言风格、测试习惯、import 风格等）编码到 memory store
- [ ] 成功率统计：工具级别、任务类型级别、时间维度

##### 7c. Curator 后台（技能管理，一期）

目标：自动维护技能库质量，去重、合并、淘汰过期技能

- [ ] 技能去重/合并：相似度分析 + 自动 propose 合并（向用户发 PR 式审批）
- [ ] 技能质量评分：使用次数 + 成功率 + 用户反馈，低于阈值则归档
- [ ] 技能过期检测：引用的文件/API 变更后标记"需验证"
- [ ] 技能使用报告：定期生成 {"最常用", "最高效", "待改进", "已归档"} 分类报告
- [ ] 定时调度：后台进程，低优先级执行（仅在 agent idle 或定时触发）

##### 7d. GEPA 式自我进化（二期）

目标：agent 自主分析失败模式，变异策略，验证改进

- [ ] 执行轨迹回顾器：读取 7b 收集的轨迹 → 识别重复失败模式
- [ ] LLM 变异 prompt：针对某个失败模式，提出改进方案（改 system prompt / 增加工具 / 调整参数）
- [ ] 实验运行器：对照组（旧策略）vs 实验组（新策略），跑 N 次任务比较成功率
- [ ] 自动 PR：实验有显著正向收益 → 自动开 PR 合入策略变更
- [ ] 安全约束：变异范围限制（不改核心逻辑、不改用户文件、不改安全策略）

##### 7e. 与现有系统的集成

- [ ] Memory store 互操作：技能执行经验写回 fact-store，供 agent 检索
- [ ] Experiment registry 对接：GEPA 实验跑在现有实验框架上
- [ ] Session compactor 输入：轨迹数据经 compact 后再做分析
- [ ] CLI 用户界面：`/skill list`、`/skill create`、`/feedback` 等命令

##### 设计原则

- **渐进式**：先做 7a skill 创建（最直观的价值），再逐步补全闭环
- **用户可控**：每次 skill 创建/合并/变异都需用户确认（PR 模式）
- **低成本**：Skill 加载 Level 0 仅 ~20 token，不影响正常对话开销
- **插拔式**：每个组件可有/可无，不开自学习也不影响核心功能

#### 方向 8：Loop 工程

- **已有**：`workflow-tool.ts`（418 行）JS 编排脚本，支持 `agent()` / `parallel()` / `pipeline()`
- **缺陷**：
  - 需要写 JavaScript，不是 AI 原生 plan-execute 循环
  - 无 session 级别 plan→execute→review 模式
- **建议迭代**：
  - [ ] AI 原生 plan-execute 循环（agent 自动：生成计划 → 逐步执行 → 验证结果 → 调整计划）
  - [ ] Plan 持久化到 session metadata，支持中断恢复
  - [ ] Workflow tool 简化，支持自然语言定义流程

### 处理原则

1. **已有完整实现的方向**（权限/压缩/子agent/CLI）→ 改缺陷、做减法，不重造
2. **半成品方向**（模式切换/loop）→ 补齐缺失结构
3. **空白方向**（自检纠错/自学习）→ 从零设计，小步迭代
4. **每个方向的实现可以是插件**（TS 脚本），别人写的/自己写/AI 写都可以
