# Satori 迭代深度分析：从 MiMoCode 学到什么

> 日期：2026-07-03
> 方法：逐模块对比 MiMoCode 源码 + Satori 源码，识别架构差距 + 迁移路径
> 审查：已通过 3 子 agent 源码验证 + 1 综合设计审查 agent，发现 23 个问题（详见第七、八章）
> 状态：**已通过 design review，待实现**

---

## 零、两个项目的根本差异

### MiMoCode（@mimo-ai/cli v0.1.4）
```
技术栈：Effect.ts + Drizzle ORM + Bun + AI SDK (@ai-sdk/*)
架构：从零构建的多 agent 操作系统
状态：全量 SQLite（session/message/part/task/actor_registry/workflow_run）
模型：多 agent 类型（build/plan/compose/general/explore/checkpoint-writer/dream...）
```

### Satori（openhanako）
```
技术栈：Node.js + Pi SDK (@mariozechner/pi-coding-agent) + better-sqlite3
架构：基于 Pi SDK 的单 agent 包装器
状态：混合（Pi SDK 管理 session/compaction，Satori 加 tool/sandbox/task registry）
模型：单一 agent（Agent 类）
```

### 核心洞察

**MiMoCode 的改进不是在 opencode 的 agent loop 上打补丁，而是重写了整个平台。**
Satori 不应该试图移植 MiMoCode 的 SQLite schema 或 Effect.ts 层，而是应该理解 MiMoCode 的设计模式，在 Pi SDK 之上构建相同的**能力**。

---

## 一、MiMoCode 的五个设计模式（按架构重要性排序）

### 模式 1：Session 作为一等公民的数据实体

**MiMoCode 做法：**
```sql
-- 每个 session 有完整的上下文继承链
session.context_from       → 从哪个上游 session 继承上下文
session.context_watermark  → 上下文水位线（重建时用到哪条消息）
session.last_checkpoint_message_id → 最近一次 checkpoint 的消息 ID
session.parent_id          → 父子 session 关系
message.agent_id           → 每条消息归属哪个 agent（main/子 agent/checkpoint-writer）
```

**Satori 现状：**
Pi SDK 的 `SessionManager` 管理 session，但：
- 无 `context_from` / `context_watermark` 概念
- 无跨 session 上下文继承
- 无 agent_id 区分（所有消息属于同一个 agent）

**可迁移性：★★★★★**
- Satori 的 `SessionCoordinator` 已经有 session 管理
- 可以通过扩展 `SessionCoordinator` 的元数据来加 context_from/context_watermark
- 不需要改 Pi SDK，在 Satori 层加元数据即可

---

### 模式 2：多 Agent 类型 + 权限隔离

**MiMoCode 做法：**
```typescript
// 每个 agent 有独立的 system prompt、permission、toolAllowlist
agents = {
  build:  { permission: {...}, mode: "primary" },     // 完整执行
  plan:   { permission: {...edit: deny}, hardPermission: {...} },  // 只读规划
  compose:{ permission: {...}, mode: "primary" },     // 编排
  general:{ permission: {...}, mode: "subagent" },    // 通用子 agent
  explore:{ permission: {...}, mode: "subagent" },    // 只读探索
  "checkpoint-writer": { mode: "subagent" },          // 内部子 agent
}
```

**Satori 现状：**
- 单一 `Agent` 类，通过 `buildSystemPrompt()` 生成一个 prompt
- `SESSION_PERMISSION_MODES` 控制权限（auto/operate/ask/read_only），但这是**会话级**而非 agent 级
- 子 agent 通过 `subagent-tool.ts` 创建，但没有独立的 agent 类型定义

**可迁移性：★★★★☆**
- Satori 的 `Agent` 类已经是 agent 抽象
- 可以扩展为**多 agent 配置**：`buildSystemPrompt({ agentType: "plan"|"build"|"explore" })`
- Plan 模式（迭代方向 1）本质上就是新增一个 agent 类型

---

### 模式 3：Actor 注册表 + 生命周期管理

**MiMoCode 做法：**
```sql
actor_registry (
  session_id, actor_id, mode, parent_actor_id,
  lifecycle: "ephemeral"|"persistent",
  context_mode: "none"|"state"|"full",
  status: "pending"|"running"|"idle",
  agent, description, tools, turn_count, ...
)
```

关键设计：
- `lifecycle: persistent` → 跨会话存活的子 agent（如 checkpoint-writer）
- `context_mode` → 子 agent 继承父会话上下文的程度
- `parent_actor_id` → agent 树形结构

**Satori 现状：**
- `SubagentRunStore`（JSON 文件）：taskId/status/parentSessionId/childSessionId
- `SubagentThreadStore`：thread 管理
- 缺：lifecycle 概念、context_mode、树形 parent_actor_id

**可迁移性：★★★☆☆**
- SubagentRunStore 已经有基础，但需要扩展字段
- 最大的挑战：Pi SDK 的子 agent session 是完整独立的 session，没有"继承父上下文"的机制
- 解决方案：在创建子 agent session 时，手动注入父会话的摘要（类似 MiMoCode 的 context_mode: "state"）

---

### 模式 4：Checkpoint Writer — 自动状态提取

**MiMoCode 做法：**
```
每个用户消息后 → tryStartCheckpointWriter()
  → 派发 checkpoint-writer 子 agent（fork 父会话前缀 + 只读工具）
  → writer 读 checkpoint.md + 对话历史 + task registry
  → 写 checkpoint.md（11 节结构化状态）
  → 写 MEMORY.md（项目级持久知识）
  → 更新 last_checkpoint_message_id

下次会话开始 → 读 checkpoint.md → 注入 system prompt → agent 知道上次做到哪了
```

**Satori 现状：**
- `SessionCompactor`：压缩对话历史（技术层面）
- `CheckpointStore`：文件快照（改动前后文件内容）
- **完全缺：** 结构化状态提取 + 跨会话恢复

**可迁移性：★★★☆☆**
- Pi SDK 的 `generateSummary()` 可以做摘要，但不做结构化提取
- 需要新建一个 checkpoint writer 子 agent
- 关键技术点：writer 需要 fork 父会话的上下文前缀（prefix cache 对齐）
- Satori 环境下，fork 可以通过创建一个新的 Pi SDK session + 注入历史消息来实现

---

### 模式 5：Compose 管线 — 自主开发闭环

**MiMoCode 做法：**
```
compose skill 加载 → 启动管线：
  brainstorm（需求 → spec）
  → plan（spec → bite-sized tasks）
  → subagent（逐 task：实现者 + 两阶段审查）
  → review（最终审查）
  → merge

每个 task 的流程：
  task create → actor spawn（绑定 task_id） → 实现 → 
  phase 1 review（spec + diff only） → phase 2 review（如有问题） →
  code quality review → task done
```

**Satori 现状：**
- `workflow-tool.ts`：JS 编排脚本（agent/parallel/pipeline）
- `subagent-tool.ts`：单个子 agent 派发
- `SkillManager`：技能系统
- **完全缺：** 把上述碎片串成管线的编排层

**可迁移性：★★★★☆**
- Satori 已有所有碎片，缺的是编排层
- workflow-tool 可以是编排引擎
- Skills 系统可以定义管线步骤
- 关键是设计每个 step 的契约（输入/输出/失败处理）

## 二、迁移路径：基于 Pi SDK 的 Satori 架构升级

### 核心原则

1. **不替换 Pi SDK** — Pi SDK 处理 agent loop + LLM 交互 + compaction，Satori 在上层加编排
2. **利用现有资产** — TaskRegistry/SubagentRunStore/CheckpointStore/FactStore 都是可用的
3. **最小可行迭代** — 先做最核心的：Task 树 + Compose 管线最简版

### 阶段一：Task 树（LLM 可见的工具）

**为什么先做这个：** 它是 Compose 管线的基础 — 子 agent 需要绑定到 task。

**实现方案：**

| 步骤 | 文件 | 说明 |
|------|------|------|
| TaskRegistry 扩展 | `lib/task-registry.ts` | 加 `parent_task_id`、`owner`、`summary` 字段 |
| LLM 可见 task 工具 | `lib/tools/task-tool.ts`（新建） | 用 Pi SDK 的 `Type.Object` 定义参数 schema，execute 内调 TaskRegistry |
| Agent 注册 | `core/agent.ts` → `getToolsSnapshot()` | 注册 task 工具 |
| 工具分类 | `shared/tool-categories.ts` | task 归入 STANDARD_TOOL_NAMES |
| 权限 | `core/session-permission-mode.ts` | task 归入 INFORMATION_TOOLS |

**关键设计决策：**
- task 工具使用 Pi SDK 的 `Type` schema 系统（与现有工具一致）
- TaskRegistry 已有 JSON 持久化，不需要切换到 SQLite
- todo_write 兼容：agent 调 todo_write 时自动同步到 TaskRegistry

---

### 阶段二：Plan 模式（设计已完成，直接实现）

**已设计文档：** `docs/迭代计划.md` 方向 1

**追加 insight（来自 MiMoCode）：**
- MiMoCode 用 **agent 类型**（而非 session mode）来实现 plan：plan agent 有 `hardPermission: { edit: deny }`
- hardPermission 不能被用户配置覆盖
- 这比 Satori 的设计更安全（plan phase + mode 切换可以被绕过）

**调整建议：**
- Satori 的 plan phase 用 `classifySessionPermission()` 拦截 SIDE_EFFECT_TOOLS
- 额外借鉴 MiMoCode：加 `hardPermission` 概念，plan 阶段的 write/edit 拦截**不可被覆盖**

---

### 阶段三：Compose 管线（最简版）

**这是 MiMoCode 最大的创新，也是 Satori 最大的机会。**

#### 最简 Compose = 3 个 skill + 编排器

```
Skill: compose:brainstorm
  输入：用户需求
  输出：需求概要（文本）
  实现：派发一个子 agent（只读工具），让它分析需求

Skill: compose:plan
  输入：需求概要
  输出：task 列表（通过 task-tool 创建）
  实现：派发一个子 agent，让它拆 task + create

Skill: compose:execute
  输入：task 列表
  输出：每个 task 的执行结果
  实现：for each task { spawn subagent → wait → 检查结果 }
```

#### 编排器实现

```typescript
// lib/workflow/compose-orchestrator.ts（新建）
async function runComposePipeline(userRequest: string, ctx: SessionContext) {
  // Step 1: Brainstorm
  const spec = await spawnSubagent({
    task: "分析以下需求，输出结构化概要...",
    agentType: "explore",  // 只读
    timeout: 5 * 60 * 1000,
  })

  // Step 2: Plan
  const tasks = await spawnSubagent({
    task: `根据概要拆成 task，用 task create 创建每个 task...\n${spec}`,
    agentType: "build",
    timeout: 5 * 60 * 1000,
  })

  // Step 3: Execute
  for (const task of tasks) {
    await spawnSubagent({
      task: `实现 task ${task.id}: ${task.summary}`,
      taskId: task.id,  // 绑定 task
      agentType: "build",
      timeout: 30 * 60 * 1000,
    })
  }
}
```

#### 与现有系统集成

| 现有组件 | 在 Compose 中的角色 |
|---------|-------------------|
| `subagent-tool.ts` | 实现者子 agent（已有，需加 taskId 绑定） |
| `task-tool.ts`（阶段一） | task 创建/追踪 |
| `SkillManager` | 存储 compose skills |
| `workflow-tool.ts` | 编排引擎（已有 JS 脚本能力） |
| `ChatSessionStore` | 子 agent 的 session 管理 |

### 阶段四：Checkpoint Writer（跨会话上下文）

#### 在 Pi SDK 环境下实现

Pi SDK 不提供"fork 父会话前缀"的能力，所以 checkpoint writer 需要另一种实现方式：

```
方案 A（推荐）：独立的子 agent session + 注入摘要
  1. 在用户消息后，Satori 触发 checkpoint 检查
  2. 创建一个新的子 agent session
  3. 注入：
     - 系统指令："你是 checkpoint writer..."
     - 摘要上下文：对话历史的关键摘要（用 Pi SDK 的 generateSummary）
     - 工具：read/write/edit（只写 checkpoint.md）
  4. 子 agent 读现有 checkpoint.md + 对话摘要 → 写更新后的 checkpoint.md

方案 B：Satori 层独立实现（不用子 agent）
  1. 每次用户消息后，用 utility model 生成对话摘要
  2. 结构化写入 checkpoint.md
  3. 不需要子 agent，但摘要质量可能不如完整上下文的 writer
```

**推荐方案 A**，因为：
- 复用现有 subagent 基础设施
- writer 可以读到完整对话历史（通过父 session 的 JSONL）
- 更接近 MiMoCode 的设计

#### Satori 实现

| 文件 | 用途 |
|------|------|
| `lib/memory/checkpoint-writer.ts`（新建） | Writer 调度 + prompt 构建 |
| `lib/memory/session-checkpoint.ts`（新建） | checkpoint.md 读写 |
| `core/session-coordinator.ts` | 新 session 创建时注入 checkpoint 到 system prompt |
| `core/agent.ts` → `buildSystemPrompt()` | 读取 checkpoint 并注入 |

## 三、实施优先级（修订版）

| 阶段 | 内容 | 改动文件 | 预估工作量 | 独立可验证 |
|------|------|---------|-----------|-----------|

## 四、结构化记忆：三文件知识管理系统（基于源码分析的完整还原）

> 本章基于对 MiMoCode `checkpoint-writer.txt`（167 行）、`checkpoint-templates.ts`（114 行）、`checkpoint.ts`（1117 行）、`memory/`、`tool/memory.ts` 的逐文件分析 + 对比 Satori `fact-store.ts`、`memory-search.ts`、`session-summary.ts`、`checkpoint-store.ts`

### 4.1 三文件架构

MiMoCode 的"结构化记忆"不是单一功能，而是一个**知识生命周期管理系统**，由三个文件 + 一个 writer 子 agent 组成：

```
会话对话流
    │
    ├─→ notes.md           ← 主 agent 自由笔记（草稿纸）
    │    ├── 记录引语、未解问题、跨项目观察、给未来自己的备忘
    │    └── 格式：## [turn N · 时间戳] + 自由文本
    │
    ├─→ checkpoint.md       ← writer 子 agent 专写（会话状态）
    │    ├── §1 活动意图    — 用户原话 block-quote
    │    ├── §2 下一步行动  — 单一具体步骤
    │    ├── §3 指令        — 本会话专属规则（非项目级）
    │    ├── §4 任务树      — 从 task DB 读取，按状态标记
    │    ├── §5 当前工作    — 检查点前正在做的事
    │    ├── §6 文件和代码  — 活跃编辑的文件
    │    ├── §7 已发现知识  — 跨任务事实（候选升级到 MEMORY.md）
    │    ├── §8 错误和修复  — 遇到的问题及解决方法
    │    ├── §9 活跃资源    — 分支、进程等运行时状态
    │    ├── §10 设计决策   — 讨论达成的结论（候选升级到 MEMORY.md）
    │    └── §11 开放备注   — 引语、未解问题、杂项
    │
    └─→ MEMORY.md           ← writer 为主 + agent 为辅（项目知识）
         ├── Project context           — 项目是什么
         ├── Rules                     — 跨会话硬约束（用户说的规则）
         ├── Architecture decisions    — 重大设计选择的 WHY
         └── Discovered durable knowledge — 从 checkpoint §7 升级的持久事实
```

**文件路径**（`checkpoint-paths.ts`）：
```
checkpoint.md  → sessions/<sid>/checkpoint.md     (per-session)
MEMORY.md      → projects/<pid>/MEMORY.md          (per-project, 跨会话)
notes.md       → sessions/<sid>/notes.md           (per-session)
global/MEMORY.md → memory/global/MEMORY.md          (跨项目, 用户手动创建)
```

### 4.2 内容流转：知识升级生命周期

这是 MiMoCode 记忆系统最精妙的设计 — **不是简单存下来，而是分级提炼**：

```
[Step 1] 会话中 agent 遇到有价值的内容
    → 随手写 notes.md（草稿纸，随时追加）

[Step 2] 检查点触发（token 阈值：上下文窗口的 20%/40%/60%/80%）
    → 派发 checkpoint-writer 子 agent
    → 读 notes.md + 对话尾部（10K-20K tokens）
    → 内容分类路由：
        会话级 → checkpoint.md 对应节
        项目级 → MEMORY.md（升级到 Rules / Architecture / Durable knowledge）
        精确字面量（DSN/端口/path/命令）→ 逐字复制，绝不改述
    → notes.md 清空回模板（内容已路由完毕）

[Step 3] 下次会话启动（或 overflow 重建）
    → checkpoint.md + MEMORY.md + notes.md 全部注入上下文
    → agent 不需要"搜索记忆"——记忆已在面前

[Step 4] 定期后台 Dream agent（每 7 天）
    → 从 trajectory DB 中提取已验证的持久知识
    → 合并到 MEMORY.md
```

**核心原则：**
- **notes.md = 草稿 → checkpoint.md = 会议纪要 → MEMORY.md = 百科全书**
- writer 是 curator，不是 transcriber — 它做判断（哪些该升级、哪些该归档、哪些该丢弃）
- 分层 scoping：会话级的不会污染项目级，项目级不会污染全局级

### 4.3 三个检索机制

| 机制 | 用途 | 实现 |
|------|------|------|
| **系统提示注入** | agent 启动时自动获取全部记忆 | MEMORY.md + checkpoint.md 内容直接注入 system prompt |
| **BM25 FTS 搜索** | agent 主动查特定信息 | `memory` tool → SQLite FTS5 (`memory_fts` 表) |
| **原始对话回溯** | 找回精确的原话/命令输出 | `history` tool → `history_fts` FTS5 |

### 4.4 Satori 当前记忆栈对比

| MiMoCode | Satori 最接近的 | 差距 |
|----------|---------------|------|
| **checkpoint.md** (11 节) | SessionSummaryManager (2 节 JSON) | 缺任务树、学习记录、错误追踪、设计决策、活跃资源 |
| **MEMORY.md** (项目规则/决策) | `CLAUDE.md` / `AGENTS.md` (只读) | **agent 不能写**项目规则；FactStore 可存但缺注入机制 |
| **notes.md** (agent 草稿纸) | **完全缺失** | 无文件、无工具、无管线 |
| **Checkpoint writer** | `deep-memory.ts`（LLM 拆分摘要为原子事实） | **不做结构化分类**，不区分会话/项目级 |
| **全局 MEMORY.md** | **完全缺失** | 无跨项目用户偏好存储 |
| **History FTS** | **完全缺失** | 无原始对话全文搜索 |

### 4.5 Satori 可落地的简化版

MiMoCode 的"知识升级生命周期"（草稿 → 分类 → 升级）目前对 Satori 的改造量太大。一期只做最核心的：

**一期（Phase 0 增强版）：**
- ✅ 写 `checkpoint.md`（compaction 完成时 hook 写入，6 节格式足够）
- ✅ 新会话读回注入系统提示
- ❌ 不做：notes.md（二期可以借鉴 FactStore 的体验模式）
- ❌ 不做：MEMORY.md 独立文件（复用现有 `CLAUDE.md` 注入 + FactStore 持久化）
- ❌ 不做：独立的 checkpoint-writer 子 agent（复用 compaction 已有的摘要生成）

**为什么一期不做 notes.md：** MiMoCode 的 notes.md 需要 agent 主动调用工具写入 + writer 在检查点时分类路由。Satori 当前没有 agent 自动写笔记的 prompt 指引，需要先在系统提示中加入"当你遇到有价值的信息时，用 search_memory 存入 FactStore"的引导。FactStore 的标签机制可以模拟 notes.md 的草稿功能。

**为什么一期不做 MEMORY.md：** Satori 的 `CLAUDE.md` 已经做了一部分（项目规则注入），FactStore 做了一部分（持久化存储）。不如增强这两个现有机制，而不是新建一个文件格式。

### 4.6 修订后的 Phase 0 改动

### 4.7 那"无限上下文"到底是什么？——同一系统的另一面

**结构化记忆和无限上下文是同一个 checkpoint 系统的两个视角：**

- **结构化记忆** = 知识管理视角（什么内容分类存到哪个文件、如何升级流转）
- **无限上下文** = 运维视角（如何用 checkpoint 替换旧消息，防止上下文溢出）

**具体机制**（从 `prompt.ts` + `checkpoint.ts` 源码还原）：

```
正常运行时：
  消息不断累积 → token 消耗上升
  → fireCheckpoints() 在 token 占比达到 20%/40%/60%/80% 时触发
  → checkpoint writer 子 agent 写 checkpoint.md（无损，11 节结构化摘要）
  → 旧消息仍然保留，checkpoint.md 只是旁路产物

溢出时（overflowCheck 检测上下文超限）：
  → hasCheckpoint(sessionID) ← 检查是否有 checkpoint.md
  → 有 → 优先用 checkpoint（无损路径）：
       insertRebuildBoundary() → 把 checkpoint.md 内容作为合成用户消息注入
       context_from/watermark 前移 → 旧消息不再出现在后续迭代
       → checkpoint 摘要 + 保留的消息尾部 = 重建的上下文
  → 没有 → 回退到 lossy compaction（有损路径）

→ 持续循环：checkpoint → 重建 → 新消息累积 → 再 checkpoint → 再重建
→ 效果：上下文永远不会真正"满"，旧内容被压缩进 checkpoint 而非丢弃
```

**这就是"无限上下文"：** checkpoint 作为旧消息的结构化压缩替代品，让 agent 可以持续工作而超出物理 token 限制。不是真的"无限"，而是压缩-重建的持续循环。

**关键发现（更正之前的错误判断）：**

之前说"watermark 是次要的"——**错**。watermark 是上下文恢复机制的核心：
- `last_checkpoint_message_id` 标记"到这条消息为止已经被 checkpoint 覆盖"
- 重建时只保留 watermark 之后的消息（尾部），watermark 之前的内容由 checkpoint.md 替代
- 没有 watermark，不知道 checkpoint 覆盖到哪，无法正确重建上下文

## 八、Design Review：关键发现与修正

> 以下内容基于对 `E:\AI_agent\MiMo-Code-main` 和 `E:\AI_agent\openhanako` 的逐文件源码审查

### 7.1 已有验证的正确假设 ✅

1. **`wrapWithSessionPermission` 拦截所有工具**（含 Pi SDK 内置 read/write/edit/bash）→ Plan 模式的工具限制有效
2. **TaskRegistry 加 `parent_task_id` 零持久化改动** → 新字段自动序列化到 JSON
3. **SubagentRunStore 可安全扩展字段** → `normalizeRun()` 用 spread 保留旧字段
4. **MiMoCode checkpoint writer 2150 行其中 80% 可跳过** → Satori 版 ~200-400 行足够
5. **`PI_SUMMARIZATION_PROMPT` 已在生成结构化摘要** → 写 checkpoint.md 只是补最后一步

### 7.2 发现的关键缺口 ❌

#### 缺口 1：双写分歧风险（Critical）

**问题：** 现有 compaction 机制已把摘要写入 session JSONL（`compaction` 条目）。如果另外写 `checkpoint.md` 且写入时机不同（如"每次用户消息后"而非 compaction 时），两份摘要内容会**分歧**。

**修正：** 不创建并行机制。Hook 到 `runCachePreservingCompactionForSession()` 中 `generateSummary()` 完成后 → 即时把摘要也写入 `checkpoint.md`。保证 checkpoint.md 是 compaction 摘要的快照副本，永不同步。

#### 缺口 2：水位线（Watermark）不可省略（Critical）

**问题：** plan 中标注 watermark 为"次要"是错误的。没有 watermark，新会话不知道摘要覆盖了哪些消息，无法正确重建上下文。

**修正：** 
- 在 `checkpoint.md` 头部记录 `watermark_message_id`（compaction 覆盖的最后一条消息 ID）
- 新会话启动时：读 checkpoint.md → 读 session JSONL 中找到 watermark 之后的消息 → `checkpoint 摘要 + tail 消息` 组成重建上下文
- 修改预估：0.5 天 → 1 天

#### 缺口 3：Plan phase 与 permissionMode 概念混淆（Critical）

**问题：** 当前代码 `session-permission-mode.ts:138` 把 `planMode === true` 直接映射为 `READ_ONLY`，这改变了 session 的 `permissionMode`。如果 agent 在 plan 阶段退出时没有正确恢复原 mode，session 会永久变成只读。

**修正：** plan phase 用**独立字段** `phase: "planning" | null`，与 `permissionMode` 正交：
```typescript
// classifySessionPermission() 检查两个维度：
if (context.phase === "planning") {
    // 只放行 INFORMATION_TOOLS，与 permissionMode 无关
}
// 否则走 permissionMode 逻辑（auto/operate/ask/read_only）
```
进入 plan → 设置 `phase = "planning"`，不改变 `permissionMode`
退出 plan → 清除 `phase`，无需恢复 `permissionMode`

#### 缺口 4：缺少 hardPermission 防护（High）

**问题：** plan 阶段如果只是 context flag，用户可以随时在 Desktop 设置面板关掉，导致半成品 plan 被执行。

**修正：** 借鉴 MiMoCode 的 `hardPermission`：
- 进入 plan phase 时设置 `hardPermission = { write: "deny", edit: "deny", bash: "deny", subagent: "deny" }`
- 用户设置**无法覆盖** hardPermission
- 只在 agent 调用 `plan_exit` 或用户显式中断时清除

#### 缺口 5：子 agent 失败无恢复协议（High）

**问题：** Compose 管线伪代码用 `await spawnSubagent()`，但 subagent-tool 的 execute 是**非阻塞**的（返回 Deferred）。如果子 agent 超时/崩溃/输出乱码，管线无人处理。

**修正：**
- 子 agent 新增 `blocking: true` 参数 → 内部用 `DeferredResultStore` 等待结果 → 超时抛错
- 失败恢复协议：

| 失败类型 | 处理 |
|---------|------|
| 超时（30min） | retry 1 次（简化上下文），再失败 → skip task，标记 `failed` |
| 输出乱码 | retry 1 次（明确格式指令），再失败 → abort pipeline |
| 权限拒绝 | 报告原因给 orchestrator，等待用户决策 |
| 崩溃 | mark task `abandoned`，继续下一个 task |

#### 缺口 6：Task 树循环引用（Medium）

**问题：** LLM 可能创建 T2 的 parentTaskId = T1，同时 T1 的 parentTaskId = T2。

**修正：** `create`/`update` 时递归检查父链，发现循环或自引用直接 reject，返回可理解的错误信息。
```typescript
function detectCycle(newParentId, existingTasks) {
    let cursor = newParentId
    const visited = new Set()
    while (cursor) {
        if (visited.has(cursor)) return true // cycle!
        visited.add(cursor)
        cursor = existingTasks.get(cursor)?.parentTaskId
    }
    return false
}
```

#### 缺口 7：任务所有权模糊（Medium）

**问题：** 子 agent A 创建任务 T1，子 agent B 能否标记 T1 为 done？

**修正：** Task 加 `owner_agent_id` 字段；子 agent 只能修改自己拥有的 task。Compose orchestrator（main agent）有覆盖权限。

#### 缺口 8：多 session 的 checkpoint 选择（Medium）

**问题：** 新会话启动时，项目下可能有多个旧 session 的 checkpoint.md，该加载哪个？

**修正：** checkpoint.md 存于 session 目录（非项目级）。新会话时扫描最近 N 个 session 的 checkpoint.md，按 mtime 排序取最新。注入时附带来源 session ID。

### 7.3 交叉关注点

| 关注点 | 发现 | 修正 |
|--------|------|------|
| **Phase 交互矩阵** | Plan phase 中 agent 能否调 task create？subagent？ | 明确：plan phase 拦截除 INFORMATION_TOOLS 外所有工具（含 task create） |
| **Token 预算** | 每新增一个工具定义 ~500-1000 tokens | 阶段完成后测量 system prompt 大小，必要时做模式感知的工具裁剪 |

| **向后兼容** | 旧 session 无 phase 字段、无 parent_task_id | 加 migration 步骤，旧 session 加载时填充默认值 |
| **测试策略** | LLM 输出不可重现 | 数据层和工具 schema 用单元测试；LLM 行为仅手动验证一次 |

## 十三、Compose 模式：Superpowers Skills 的 Satori 迁移分析

> 基于对 MiMoCode `agent.ts:198-212`（compose agent 定义） + `compose/*/SKILL.md`（15 个 skill） + `workflow/builtin/compose.js`（749 行） + Satori `workflow-tool.ts`（418 行） + `subagent-tool.ts`（959 行） + `SkillManager` 的逐文件对比分析

### 13.1 Compose 模式到底是什么

**Compose 是三层叠加：**

```
Layer 1: Agent 类型（14 行定义）
  └── agents.compose = { name:"compose", mode:"primary", permission:... }
      与 build/plan 同级，权限几乎一样。关键区别在 Layer 2。

Layer 2: System Prompt 注入（prompt.ts 在检测到 agent="compose" 时触发）
  ├── 注入 compose.txt（119 行系统提示，告诉 agent "你是编排者"）
  └── 注入 <compose_skills> XML block（列出 compose 专属 skills）

Layer 3: 15 个 Skills（superpowers 方法论）
  ├── compose:brainstorm  — 需求澄清 + 方案对比
  ├── compose:plan       — 拆成 bite-sized tasks
  ├── compose:subagent   — 逐 task 派发子 agent + 两阶段审查
  ├── compose:execute    — 内联执行（不派子 agent）
  ├── compose:verify     — "没有新鲜验证证据就不能声称完成"
  ├── compose:report     — 生成最终报告
  ├── compose:merge      — 合入分支
  ├── compose:review     — 代码审查
  ├── compose:debug      — 系统化调试（4 阶段）
  ├── compose:tdd        — 红-绿-重构循环
  ├── compose:worktree   — 隔离工作区
  ├── compose:ask        — 结构化提问
  ├── compose:feedback   — 接收审查反馈
  ├── compose:parallel   — 并行派发子 agent
  └── compose:new-skill  — 元 skill（创建新 skill）
```

**完整管线（交互模式）：**
```
用户请求
  → compose:brainstorm  (澄清需求，提 2-3 种方案，HARD-GATE：未经批准不实现)
  → compose:plan        (拆成 bite-sized tasks，每 step 2-5 分钟)
  → compose:subagent    (逐 task：实现者子 agent → 规范审查 → 代码质量审查)
       ├── compose:tdd  (子 agent 走红-绿-重构)
       └── compose:review (审查者子 agent)
  → compose:verify      (跑验证命令，确认通过)
  → compose:report      (写最终报告)
  → compose:merge       (合入分支)
```

**为什么叫 "superpowers"：** 这些 skill 编码了软件工程方法论——TDD、两阶段审查、结构化提问、根因分析——每条都是"铁律"级别的约束（如 compose:verify："NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE"）。

### 13.2 Satori 已经有 Compose 所需的基础设施

**结论：没有根本性架构障碍。** 逐项对比：

| Compose 需求 | Satori 对应组件 | 状态 |
|-------------|---------------|------|
| 管线引擎 | `workflow-tool.ts` + `host-api.ts` | ✅ 支持 `agent()`/`parallel()`/`pipeline()`/`workflow()`/`phase()`/`log()` |
| 派发带自定义 prompt 的子 agent | `subagent-tool.ts` → `executeIsolated(prompt, opts)` | ✅ 任意 task prompt，可按 agent 名称定位 |
| 限制子 agent 工具权限 | `subagent-tool-policy.ts` → read/write 两种模式 | ✅ toolFilter + builtinFilter |
| 结构化输出 | `workflow/structured-output.ts` | ✅ JSON schema |
| Skill 托管 | `SkillManager` + `SKILL.md` 格式 | ✅ YAML frontmatter，自动加载 |
| 管线断点续传 | `workflow/journal.ts` → SHA256 key matching | ✅ 重跑跳过已完成节点 |
| 并发控制 | `workflow/concurrency.ts` → 256 并发 | ✅ 原生支持 |
| Sandbox 安全 | `workflow/sandbox.ts` → Node.js vm context | ✅ 无 require/process/fs/net |

**最简 Compose 脚本（现在已经可以在 Satori 上跑）：**
```javascript
export const meta = { name: "compose-minimal", description: "最简 compose" };

phase("brainstorm");
const spec = await agent(`分析需求: ${args.request}`, { access: "read" });

phase("plan");
const tasks = await agent(`拆成子任务: ${spec}`, { access: "read" });

phase("execute");
const results = await pipeline(parseTasks(tasks), async (task) => {
  return await agent(`实现: ${task}`, { access: "write" });
});
```

### 13.3 还缺什么：集成工作而非架构缺口

| 缺口 | 严重度 | 状态 |
|------|--------|------|
| **Task 树层级** | Critical | `todo_write` 扁平替换式，缺 `parent_task_id`（→ Phase 1） |
| **阻塞式子 agent 等待** | Critical | `subagent-tool.ts` fire-and-forget；workflow-tool 内部已阻塞；对上层需要 `blocking:true` 参数 |
| **Plan phase 守卫** | Critical | planMode→READ_ONLY 需改为独立 `phase` 字段（→ Phase 2） |
| **子 agent 失败恢复** | High | 无 timeout→retry→skip 链 |
| **Compose skill .md 文件** | 内容层 | 纯 markdown，写就完事 |
| **Compose workflow 脚本** | 内容层 | 纯 JS，写就完事 |
