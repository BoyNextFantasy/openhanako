## 1. 项目介绍

Satori 是一个基于 Pi SDK 构建的本地 Coding Agent，对标 Claude Code / Codex，提供桌面端应用。核心要解决的问题是：一个 Agent 不能只会调工具——它需要**安全地**操作本地文件、**先规划再动手**、在多轮长对话中不迷失方向、并**跨会话记住**用户的经验和偏好。我负责设计和实现了四块核心能力：**权限防线**、**上下文管理**、**Plan 模式**、**记忆系统**，并用一套分层自动化测试体系（6900+ 条用例、typecheck + 全量回归作为提交门禁）保证这套体系的每次迭代都可验证。

## 2. 面试问答

### 一、权限防线

### Q1. ⭐ 5 层防线具体每层做什么？为什么是这个顺序？

把它想成一条命令的旅程——任何一层拒绝即终止，拒绝原因会作为工具结果带回给模型。第一层硬编码命令拦截在最外层直接拒绝危险命令，不经过模型判断；拦截分两级：递归强删文件系统根，直接拒绝; 高危写操作——改注册表、这类，非 operate 模式强制转人工确认。命令解析先拆引号转义，再递归解包，PTY 标准输入注入的字符也纳入检测，防止包装绕过。第一层用硬编码而不是 AI，是因为它便宜、确定。第二层会话级权限判定根据当前权限模式过滤可用工具。第三层 AI 安全评审用独立于主模型的评审模型审操作意图，风险未知的升级到确认层。第四层 OS 沙箱通过受限令牌降权，在子进程里隔离执行：凭证文件读不到、.git 写不了、系统目录不可碰。第五层用户确认弹窗，用户看得见命令全文，高风险操作由人拍板。顺序原则是越前置越便宜不经过模型，越后置掌握的信息越多拦截越精准但成本高。五层都过了也有风险——所以不承诺绝对安全，承诺的是**层层设防加全量留痕**：会话 JSONL 可回放每条工具调用，出了问题能定位到哪一层放行、为什么放行。

> ⚠️ 注意：第三层 AI 安全评审仅 AUTO 模式下触发

### Q2. AI 安全评审那一层，模型自己审自己，会不会放水？怎么保证它不误判？

评审是独立的双模型流水线：小模型先初筛，判定低风险放行即通过；非低风险升级大模型终审。两个模型都不和主模型共用提示词，评审提示词聚焦安全判断不看业务逻辑，输出限定四类动作：放行、拒绝并继续、询问用户、升级确认。防放水有两道设计：小模型对高风险操作给放行会被强制升级大模型复核；评审模型不可用或输出不合法时一律兜底弹人工确认，宁可多弹不能漏。评审只审工具参数不审执行结果——参数是 Agent 可控的所以必审，结果由 OS 沙箱兜底，不需要模型再评一次。整套评审只在 AUTO 模式触发，其他模式本来就有确认或拦截兜着。

### Q3. ⭐ OS 沙箱是怎么实现的？

采用的不是虚拟机方案，而是系统原生隔离，三个平台各有后端：Windows 受限令牌、macOS Seatbelt、Linux bubblewrap。以 Windows 为例：进程用 CreateRestrictedToken 降权后启动，只有工作目录等白名单可写，系统目录写不进去。两类保护是配置化生成的：**凭证防读**——auth.json、models.json 这类密钥文件和 browser-data 等目录进 OS 级拒绝读取列表，Agent 拿不到 API 密钥；**版本历史防写**——每个工作区的 .git 目录在可写范围之内再单独设为拒绝写入，Agent 能改代码但不能篡改版本历史。核心思路不是信任模型，而是假设命令可能有害、通过多层限制让它做不了坏事。

### Q3-1. 这条链路怎么留痕？出了问题能回溯吗？

三类数据是全量持久化的：会话历史按 JSONL 全量落盘，工具调用和结果都在其中，可逐轮回放；LLM 用量台账每条请求记录模型、耗时、token 用量和业务归因，持久化存储并出可视化图表；任务树状态跨轮次持久化，每步进展可回看。权限决策以工具结果消息的形式留在会话记录里，附带评审结论和命中的规则 ID。独立的命令级安全审计日志在规划中，目前先接入了 HTTP 和资源访问两处。

### 二、上下文压缩

### Q4. ⭐ Context 快满了怎么办？压缩怎么设计？

在 Pi SDK 原生压缩引擎之上叠加了三层治理。

第一层**工具输出修剪**：压缩前先把旧轮次里大文件读取结果清掉——那些内容当时有用过后就是噪声，清除后既能直接缩小上下文，也让后续压缩质量更高。第二层**缓存保留压缩**：在同一个缓存前缀上生成结构化摘要，按任务、文件、过程三个维度组织——记目标、进度、阻塞点和关键上下文，记改了什么文件，记约束、关键决策和失败原因——外加文件操作清单。因为前缀没变，大模型的缓存可以复用，避免了每次压缩都重新编码整个上下文。第三层**硬截断兜底**，压缩后仍超限走截断防死锁。另加两道保险：1.**防抖计数器**在反复压缩时强制阻断循环；2.压缩后从原始来源重新加载项目规则和记忆，防止摘要代际衰减。

### Q4-1. 上下文压缩什么时候触发？

两种情况。一是用户主动调用压缩命令，比如 `/compact`，手动触发即时压缩。二是系统自动检测——Agent 每次模型调用后会计算当前上下文累计消耗的 token 数，当逼近模型上下文窗口限制或预设的安全水位线时，自动触发压缩，把一个已经太长的上下文窗口压回可用范围。

### 三、Plan 模式

### Q5. ⭐ Plan 模式是怎么设计的？

Plan 解决的是"想清楚了再动手"。它是一个**只读权限模式**：在工具层限制 Agent 只能读代码、搜文件、跑类型检查和定向跑测试这类只读操作，不能写文件或执行有副作用的命令。配套三个设计：一是 **Question 结构化提问工具**——需求模糊时模型在规划阶段就把问题列出来问用户，把模糊需求澄清成明确目标，而不是带着误解往下做；二是**结构化计划书**——调研完成后提交包含目标、步骤、风险、验收标准的计划，用户在界面上看到的是一张可审阅的计划卡，可以确认也可以拒绝；三是**确认即开工**——用户确认后系统自动把计划生成一棵可视化的任务树（每步是独立节点，五态流转：待办、进行中、阻塞、完成、放弃），并切入执行模式逐个推进，进度实时反映在界面上，重启不丢。

### Q5-1. 子 Agent 派遣、多 Agent 协作怎么避免互相干扰？

两个关键机制。**共享任务树**——多 Agent 读写同一棵任务树，各自认领节点，主 Agent 通过树的状态聚合进度，设计上让改动面不重叠，避免重复劳动。**权限固定边界**——子 Agent 的权限永远不能超过父会话：固定黑名单高于一切权限模式，禁止子 Agent 自递归再派任务、写长期记忆、对外发通知这类副作用，这个边界配置都改不了。会话间状态隔离靠 session 级无状态沙箱，互不持有对方状态。

### 四、记忆系统

### Q8. ⭐ 记忆系统怎么设计？短期长期怎么分工？

短期记忆在单次会话内生效，核心就三块：对话历史本身由框架维护的消息流；**任务树**结构化记录做了什么、正在做什么、什么被阻塞了；以及每十轮、会话结束和每天定时生成的滚动摘要，提取用户画像事实后编译进长期记忆文件。

长期记忆跨会话共享，基于 **SQLite** 存储。每条记忆是一个元事实，比如"用户偏好xxx"。由模型从定时构建的滚动摘要中批量提取元事实，带标签存入，检索时用标签匹配加 **FTS5** 全文搜索。产物最终编译成记忆文件按需注入系统提示词，让 Agent 跨会话记住用户偏好。此外还有**置顶记忆、可编辑记忆和记忆开关**——用户发现记错了可以直接在对话里纠正，开关关了就不写入不读取，防止污染。

#### Q8-1. 追问和上下文压缩的摘要的回答
上下文快满时另有一套独立的压缩机制，把早期对话压缩为结构化摘要但保留当前目标、已改文件和失败测试不丢，不经记忆系统。

#### Q8-2. 长期记忆按需检索召回吗？什么情况下需要检索？

两条路径。被动注入——每次会话启动时直接注入进系统提示词，Agent 不做任何操作就能看到近期记忆。主动检索工具供模型按需调用，当模型判断当前任务可能涉及历史事实时才触发，用 LLM 生成的标签加 FTS5 关键词去SQLite搜索，不是每次都搜。

#### Q8-3. 长短期记忆是同时注入吗？

是。两者共存于每次对话的上下文窗口——长期记忆在系统提示词里作固定前缀，短期记忆在消息流里随对话增长。

#### Q8-4. 置顶记忆是如何实现置顶的？和长期记忆如何区分开？

普通记忆走自动管线：滚动摘要提取→SQLite→定期合并注入提示词，容量有限可能丢失低频记忆。置顶记忆走独立存储——1.可以是工具直接写入独立的 JSON 文件，全程不经过 SQLite，不截断，合并；2.自动管线生成的记忆也能被用户选择置顶到独立文件。两者在提示词里分层摆放，置顶记忆坐在长期记忆上方，标记为用户要求始终保留，不受管线容量影响。

#### Q8-5. 记忆为什么编译成文件放提示词末尾，而不是每次动态检索？

两个原因。第一是成本和确定性——被动注入不需要模型主动想起来去查，会话启动就有；第二是缓存前缀——系统提示词里记忆编译产物放在缓存分界线之后、提示词最末尾，前面所有静态内容（工具定义、项目规则、记忆使用规则）的前缀缓存都能命中，记忆更新不会打碎缓存。主动检索工具是补充，模型判断当前任务涉及历史事实时，才用标签加全文搜索去查库，不是每次都搜。

#### Q8-6. 中文记忆搜索怎么做的？FTS5 默认分词对中文不友好吧？

对，FTS5 默认 unicode61 分词器按空格切词，中文会退化成整句匹配。做了两层处理：写入时把原文和标签生成 2/3-gram 拼进检索文本列，FTS5 用外部内容表模式加触发器同步；查询词同样做 ngram 扩展再匹配。FTS 无结果或语法错误时降级 LIKE 模糊搜索兜底。标签匹配是另一条路：标签存 JSON 数组，用 json_each 展开精确匹配、按命中数排序。所以中文检索实际是"标签精确匹配 + ngram 全文 + LIKE 降级"三层。

### Q9. 为什么用 SQLite + FTS5 而不是向量数据库？

SQLite 是嵌入式关系数据库，FTS5 是它内置的全文搜索扩展，能高效做关键词匹配。记忆的存入和检索两端都是 LLM 在生成关键词——存入时从对话提取标签写入，检索时根据当前任务生成查询词用全文搜索匹配。两边的用词习惯天然一致，不需要嵌入模型做语义翻译。v1 用向量方案时发现嵌入偏差反而导致召回不准，v2 切到标签匹配后效果没差但去掉了向量模型的依赖和计算成本。本质不是语义相似度搜索，而是模型自己写的标签自己搜。

### 五、通用架构与工程

### Q10. ⭐ 先整体介绍一下你的本地 Coding Agent 项目，从输入任务到最终修改代码，完整链路是怎样的？

收到任务后分三步：**准备、执行、收敛**。

准备阶段先恢复会话上下文——工作目录、历史对话、权限模式、模型配置、项目规则和相关记忆——然后判任务类型：需求模糊用提问工具先澄清，复杂改动先进 **Plan 只读模式**读代码、拆任务、列风险，用户确认后再切到操作模式执行。执行阶段模型不直接碰文件，而是通过工具层把决策翻译成读文件、搜索代码、编辑、跑测试等动作，每次调用前穿过**权限管道**——Plan 模式只能读，写文件和命令需要对应权限，危险命令直接拒绝。收敛阶段失败不报错退出，错误信息带回下一轮让 Agent 缩小范围重新修复，最终用测试通过、类型检查零错误、人工验收完成闭环。不是一次性撞对，而是**生成→验证→发现问题→带着证据再修→再验证**的收敛循环。

### Q11. ⭐ 你项目里的工具系统是怎么做的？

遵循 Pi SDK 的 工具定义规范。底层由 Pi SDK 转发为模型厂商的工具调用格式。在此基础上工具系统解决四件事：按权限模式和工作流过滤可见工具、失败信息带回下一轮、结果回写对话记录。设计上有两个关键理念——一是渐进式披露，而是根据当前会话模式动态控制可见范围，并且只提供工具描述词；二是工具描述的质量直接决定调用准确率。

### Q11-1. 工具你会用 MCP 吗？还是自己写？大模型工具实现有什么好处？

MCP 是工具/数据源的标准协议，解决工具跨模型、跨 Agent 复用；Function Calling 是模型↔工具的协议。我项目里底层用 Pi SDK 的工具定义规范，内部工具都是自己写的（文件读写、命令执行、搜索、记忆检索），因为内部工具要深度绑定权限、沙箱、审计。好处是结构化 schema——工具名、描述、参数 schema 让模型学会"什么时候调、怎么调"，工具描述质量直接决定调用准确率，所以我把工具描述当一等公民对待。MCP 的价值在生态接入，自己写工具的价值在深度控制。

### Q12. 工具调用失败时，Agent 是直接报错还是做恢复和重试？

关键是区分**可恢复的错误**和**不能绕过的安全边界**，否则重试很容易变成乱试。

可恢复的情况：文件不存在就把错误返回给模型，让它重新搜索路径或者问用户；命令超时保留已有输出，缩小测试范围再跑；测试失败把失败用例和错误栈带回下一轮对话，让模型根据具体错误信息定位修复。不可恢复的情况：权限不够就是安全边界，系统直接硬拦截，弹给用户确认或在只读模式下直接拒绝，不能让模型自己绕过。我的原则就一条：普通错误给模型足够信息让它继续修复，安全错误必须由系统兜底拦截，不能靠模型自觉。

### Q13. ⭐ 支持不同模型后端吗？怎么抽象请求格式、响应结构、错误码和重试逻辑？

支持。核心思路是把**模型标识和模型服务商分开**——同一个模型名可能来自不同供应商，配置里独立记录密钥，模型能力等。利用pi-sdk能力，接入多家时做一层**适配层统一入口**：上层 Agent 只需要知道"我要发一段对话、有哪些工具可以用、要边生成边返回"，不关心底层是 OpenAI 还是 Anthropic 的格式差异，适配层负责把各家格式转成内部统一结构。

### Q14. Agent 反复读同一文件或调同一工具，怎么识别？

从三个层面来看。文件层面，记录最近读过哪些文件以及文件摘要是否变化——如果内容没变，重复读取时可以提醒已有结果。工具层面，记录相近时间段内同一个工具被调用过的参数组合，如果完全重复就提醒避免无效调用。任务层面，用**任务树**结构化记录已经完成什么、正在做什么，减少模型因为忘记进度而去重复操作。

但我不会强行拦截所有重复。比如文件刚被修改后重新读一遍是完全合理的。更好的做法是**提醒加统计**，让 Agent 自己判断要不要跳过，而不是粗暴禁止，否则反而会影响正常的工作流。

### Q16. 为什么用 Pi SDK 而不是 LangChain 或 LangGraph？

Pi SDK 是开箱即用的 Agent 运行时——会话管理、工具执行、权限管道、流式推送这些能力已经内置好了，我们可以在这个基础上专注做策略层的设计，比如五种权限模式怎么定义、Plan 工作流怎么编排。LangChain/手搓的优势在另一面：你可以精确控制每一步模型调用，出问题时调用栈更透明、更容易定位和修复，基础设施得自己从零搭建。选型本质上是在"基础设施开箱即用"和"执行链路完全可控"之间做权衡——对我们这个需要快速迭代的本地 Agent 场景，Pi SDK 的集成度更匹配。

### Q17. task 工具和任务树是干什么的？

任务树是 LLM 可见的树形工作项，跨轮次不丢失，不占用上下文。用于 Plan 模式下创建计划表，切到操作模式后逐个推进。每个节点五态流转：open（待办）→ in_progress（进行中）⇄ blocked（阻塞）→ done（完成）/ abandoned（放弃）。子 agent 读写同一棵树，实现多 agent 协作拆分。任务按会话归属过滤，界面上右侧有实时的任务计划卡，用户能看到进度；状态持久化在磁盘上，应用重启任务树还在，用户也可以在界面上手动把某个任务标记完成或放弃。

### 六、提示词设计

> **背诵主线（一段话，任何提示词问题都用它开场）**：我的提示词不是几段文案，是**代码在运行时组装的系统**，四条设计逻辑——①**静态在前、动态在后**，中间一条缓存分界线，护住前缀缓存；②**行为约束写显式清单**，不指望模型自己领悟；③**结构化输出靠 schema 不靠恳求**；④**摘要类输出靠"代码兜底 + 校验修复"**。面试官从任何角度切入，先背这段总纲，再按切入点展开对应卡片；工具描述归 Q11，记忆为何放末尾归 Q8-5，不重复背。

### P1. ⭐ 总纲 + 系统提示词结构（切入：整体怎么设计的/系统提示词里有什么）

开场背总纲，然后展开第①条：静态前缀是各段行为准则——执行环境（XML 包裹的平台/cwd/沙箱模式）、输出纪律、工具使用纪律、失败处理（先诊断再换方向，不盲目重试）、操作安全（暂停确认的代价很低，误操作的代价很高）、网页工具三级优先级。分界线之后是动态尾部——用户档案、人格、Plan 指令、工作区规则（git 根到 cwd 逐级收集的 AGENTS.md，声明只对本工作区生效）、记忆编译产物、当前时间。语言策略一句：主提示词中文，工具描述英文。

> 追问：为什么静态动态分开？→ 缓存按严格前缀匹配，会话间会变的（记忆/时间/用户档案）放分界线后，更新不打碎静态部分的缓存。

### P2. Plan 提示词（切入：Plan 怎么引导模型/结构化计划怎么保证）

提示词给流程，权限给硬约束。流程是 5 步：通读现状别急着写方案 → 不明确就用 question 工具问 → 提问优先 → 澄清后必须调 plan_submit 提交计划 → 提交后不要动手等确认。**结构化靠 schema 不靠恳求**：plan_submit 强制七字段（目标/范围内/范围外/步骤/风险/测试计划/确认点），每步强制验收标准，不合格的计划交不出来。工具返回文本再刷一遍指令："卡已提交，等用户确认，别动手"——长对话稀释了系统提示词也有这道保险。

### P3. 摘要/提取提示词（切入：压缩/记忆的 prompt 输出不可靠怎么办）

四条：①**格式给死**——压缩摘要六段固定结构，要求保留精确路径、函数名、报错原文；②**代码兜底**——文件操作清单由代码从工具调用记录提取，不劳模型，模型只做语义归纳；③**边界写死**——记忆提取设定"记忆拆分器"身份、差分模式找新增、排除清单，判别标准一句话："宁可漏，不可错"；④**校验修复**——格式契约单源维护，产出做结构校验，不过允许 LLM 修一次，且明令"只修格式，不动事实"。

### P4. 安全评审提示词（切入：评审 prompt 怎么写/会不会被绕过）

三句：①输出契约 JSON only——动作四选一（放行/拒绝并继续/询问用户/升级确认）加风险四级；②职责边界写死——"只替代人工批准，无权扩大沙箱和网络策略；灾难请求到你这也不准批"，双模型分工同一段词（小模型只放明显低风险，大模型做终审）；③调用工程——temperature 0、限 220 token、15 秒超时、长输入截断。被绕过怎么办：评审只审参数不替用户决策，后面还有权限模式和 OS 沙箱——**词可诱导，沙箱不可**。

> 工具描述也是提示词，一句话带过：question 工具在描述里教模型"批量提问省轮次""推荐项放首位标 Recommended"——细节见 Q11。

### 七、测试体系

### Q18. ⭐ 6900+ 条测试怎么做到的？分层是什么？

测试和功能同分支交付，不后补——每做一项功能，对应测试文件跟代码进同一次提交。分四层：**契约层**测公共行为、权限和协议边界，比如权限模式对工具可见性的过滤规则；**单元层**测纯逻辑的稳定输入输出；**路由层**测 HTTP/WS 边界的鉴权、错误形状和资源范围；**UI 层**覆盖 React 组件、状态 store 和自定义 hooks。合计 6900+ 条用例、800+ 个测试文件，前后端全覆盖。提交门禁是 typecheck（3 个 tsconfig，0 错误）+ vitest 全量回归，不绿不合入。

### Q18-1. 有没有难测的东西？举个有技术含量的例子。

交互式工具。比如 Question 提问工具，execute 内部 await 一个等待用户回复的 Deferred Promise，直接调用会永远挂起，测试跑不完。解法是利用 JS 事件循环的时序特性：async 函数执行到第一个 await 之前，所有同步代码都已执行完——execute 一启动，事件回调里已经同步拿到问题 ID；测试从外部调 reply() 把这个 Deferred resolve 掉，再 await execute 的返回 Promise 拿结果断言。这套模式解决"要等外部输入的工具没法自动化测试"的问题，复用到所有交互式工具上。

## 3. 场景题专区

> 面试官现在倾向用"现实开发中遇到的问题"来提问，这些场景题从具体情境切入，考查你把系统设计落到真实问题上的能力。回答套路：先给判断和处理思路，再展开系统里哪套机制在兜底，最后接得住追问。

### S1. 长会话失忆

**场景**：用户开了一个 40 轮的长会话。前 20 轮让 Agent 重构了某个模块并改了好几个文件，后 20 轮换了任务。现在用户问"之前重构时那个接口为什么改成回调了？"，Agent 有点答不上来。你会怎么处理？

**思路**：三层机制兜底，Agent 不会真的失忆。第一，**任务树**——结构化记录做了什么、正在做什么、被什么阻塞，跨轮次持久化不丢失，翻任务树就能对齐当时的进度。第二，**上下文压缩摘要**——摘要按任务、文件、过程三维组织，明确记录"改了什么文件"加文件操作清单，压缩后这些上下文仍保留。第三，**工具层**——代码事实优先于记忆，Agent 可以直接重新读目标文件拿最新事实，重复读取还有内容摘要变化检测提醒。

[追问]

> 压缩把细节丢了怎么办？

摘要代际衰减问题专门修复过：压缩后从原始来源重新加载项目规则和记忆；涉及代码的事实直接从代码重新读，不依赖摘要记忆。

### S2. 被提示词诱导执行危险命令

**场景**：用户（或一段精心构造的提示词）诱导 Agent 执行危险操作，比如 `git push origin main --force`，或者 `bash -c "git push -f"` 这种包装形式，甚至 `rm -rf /` 这种毁灭性命令。系统怎么反应？

**思路**：第一层硬编码拦截直接拒绝，不经过 AI 评审也不弹确认。灾难红线（递归删根、删盘符根、格式化磁盘、diskpart、mkfs）任何权限模式都直接拦；强推这类危险变体同样直接拦；命令解析器处理引号和转义，并递归拆解嵌套的命令包装（bash -c、cmd /c、powershell -command 最多三层），防止包装绕过；连向已运行进程的标准输入注入危险命令字符也会被检测到。拦截后返回结构化错误给模型，模型拿到的信息是"该操作被安全策略拒绝"加命中的规则 ID。

[追问]

> 用户真的想强制推送怎么办？

拦截的是 Agent 工具层的行为，用户可以在自己的终端操作；这是设计取舍：宁可误拦不可漏拦，Agent 不提供危险路径。

> 怎么识别包装过的命令？

命令先拆掉外层包装，再对内部命令做同样的黑名单检测，不信任模型自报的命令。

> 高危但不是灾难级的呢？比如改注册表？

那是第二级：非完全信任模式下强制升级到人工确认，由用户拍板；完全信任模式（operate）放行——信任档位是用户自己选的，选了就自担。

### S3. 两个子 Agent 并发改同一文件

**场景**：你派了两个子 Agent 并行干活，一个在改 a.ts，另一个也要动 a.ts，或者两个都要改配置文件。会不会互相覆盖、把文件写坏？

**思路**：三层防护。第一，**任务划分**——共享任务树让子 Agent 各自认领节点，主 Agent 按树聚合，设计上尽量让改动面不重叠。第二，**会话级无状态沙箱**——每个子会话独立隔离，不持有引擎级共享状态，互不干扰。第三，**文件级原子写**——真出现同文件竞争时，写入是原子的，不会产生半个文件；一致性由文件系统保证。

[追问]

> 子 Agent 的权限边界？

永远不能超过父会话，固定黑名单防止它自己再造子任务、防止往长期记忆里乱写，这个边界改不了。

### S4. 跨会话记忆

**场景**：上周用户让 Agent 做项目时明确过几个约束（比如"测试用 vitest 不用 jest""提交信息用中文"），这周开了个全新会话继续开发。Agent 还记得这些约束吗？怎么做到的？

**思路**：记得，靠**跨会话长期记忆**。上周会话运行中，滚动摘要管线（每 10 轮/会话结束/每日三级）从对话里提取"带标签的元事实"存进 SQLite；新会话启动时，记忆编译产物按"事实/今日/本周/长期"四层直接注入系统提示词尾部——Agent 不用主动查，开场就知道这些约束。会话中模型判断当前任务涉及历史事实时，还可以主动调记忆检索工具，用标签精确匹配加全文搜索补查。记错了也有纠正机制：置顶记忆不被管线淘汰、可编辑记忆直接在对话里纠正、记忆开关关了不写入不读取。
