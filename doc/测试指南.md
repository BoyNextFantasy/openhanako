# 测试指南

## 为什么写这个

此前验收 Question 工具时，尝试了错误的测试方式：启动服务器进程 → curl API → 人工观察。不仅耗时、每次都要等启动，而且根本测不到要测的东西（工具逻辑被埋在 LLM 调用链里，无法从外部直接触发）。

读了 `tests/` 目录后，发现项目已有完整的 vitest 测试体系（802 个文件、6874 个测试），所有工具、服务、路由都有对应的测试模式可以借鉴。

## 先读：现有测试模式

`tests/README.md` 定义了分层：
- `contract` — 公共行为、权限、协议边界
- `unit` — 纯逻辑、稳定输入输出
- `route` — HTTP/WS 边界（auth、错误形状、资源范围）
- 等等

**不要猜，先读现有测试。** 找到最接近你要改的模块的测试文件，照着它的结构写。

## 技术栈

- 框架：vitest v4
- 配置：`vitest.config.js`（有 path alias，注意 `@/` 映射到 `desktop/src/react`）
- 命令：
  - `npm test` — 全量
  - `npx vitest run tests/xxx.test.ts --reporter=verbose` — 单文件
  - `npx tsc --noEmit` — 类型检查

## 交互式工具（如 question）的测试方案

### 问题
`execute` 内部 `await` 一个 Deferred Promise（等待用户/外部回复），调用 `execute` 后 Promise 会挂起，一直不 resolve。

### 解法
利用 JS 事件循环特性：`async function` 执行到 `await` 之前，所有同步代码（包括 `questionService.ask()` 的 `emitEvent` 回调）都已执行完毕。在挂起后，从测试代码外部调用 `reply()` resolve Deferred，然后 `await execute()` 的返回 Promise。

```
const resultPromise = tool.execute("tc-1", params, null, null, mockCtx)
// 此时 capturedId（来自 emitEvent 回调）已经被同步写入
questionService.reply(capturedId!, [["Red"]])
const result = await resultPromise
expect(result.content[0].text).toContain("Red")
```

### 时序原理

```
测试线程                                 execute 线程
  │                                        │
  ├─ tool.execute(...) ──────────────────►  │
  │                                        ├─ ctx.emitEvent({id, ...})  ← 同步执行
  │                                        ├─ await questionService.ask()
  │                                        │     (挂起)
  │◄── resultPromise (pending) ────────────┘
  │
  ├─ questionService.reply(capturedId,     │
  │   [["Red"]])                           │
  │                           ──────────►  ├─ Deferred resolve
  │                                        ├─ 继续执行
  │◄── result (resolved) ──────────────────┘
  │
  ├─ assert result
```

### 关键约束
- 不能在 `execute` 之前调用 `reply()` — Deferred 还不存在
- `emitEvent` callback 必须是同步的，不能在 `setTimeout`/`nextTick` 里调用
- 单例状态（如 `questionService` 的 `pending` Map）必须在 `afterEach` 里清理，否则跨测试泄漏

## 单例测试的注意事项

如果被测试的模块有模块级可变状态（如 `questionService` 的 Map），必须：

```ts
afterEach(() => {
  for (const entry of questionService.list()) {
    questionService.reject(entry.id)
  }
})
```

否则：
- 测试 A 调用 `ask()` 但不 reply → 状态留在 Map 里
- `afterEach` 清理时 reject 那个 Promise → **Unhandled Rejection**（Promise 没有被任何 `await` 消费）
- 即使在测试 B 开始前清理，清出来的 Promise rejection 也是未捕获的

正确做法：测试内自己 reply/reject 所有 ask 的 Promise，`afterEach` 只作为安全网兜底。

## 不要这样验证

### ❌ 不要启动服务器 + curl
```
启动服务器（等 10s）→ curl API（403 鉴权）→ 啥也测不到
```
慢、不可靠、测不到工具内部逻辑。

### ❌ 不要自己在 Agent session 里测试
Agent 不能在自己的对话里调用自己的 question 工具。

### ❌ 不要写端到端测试来验证工具逻辑
WS 广播 → Desktop Modal → 用户点击 → WS 回传 这条链路应该单独写集成测试（如果值得测的话），而不是跟工具 execute 的测试混在一起。

## 正确的验收步骤

1. `npx vitest run tests/xxx.test.ts` — 单文件测试
2. `npx tsc --noEmit` — 类型检查
3. `npm test` — 全量回归（确保无新增失败）
4. `npm run build:renderer` — Desktop 构建（如果改了前端/Desktop 代码）

从第 1 步开始，不要跨界跳到第 4 步。
