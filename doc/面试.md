## 1. 项目介绍

Satori 是一个基于 Pi SDK 构建的本地 Coding Agent，对标 Claude Code / Codex，提供 Electron 桌面端应用。核心要解决的问题是，一个 Agent 不能只会调工具——它需要安全地操作本地文件、在多轮长对话中不迷失方向、记住跨会话的经验和偏好、甚至在没有用户消息时主动巡检工作区。我负责设计和实现了支撑这套能力的五个核心子系统：**权限防线**、**上下文压缩**、**Plan / Compose 工作流**、**主动巡检与定时任务**、**记忆系统**。

## 2. 面试问答

### 一、权限防线

### Q1. 5 层防线具体每层做什么？为什么是这个顺序？

第一层硬编码命令拦截在最外层直接拒绝已知危险模式，不消耗模型令牌。第二层会话级权限判定根据当前权限模式过滤可用工具。第三层 AI 安全评审用独立的轻量模型审操作意图，风险未知的标记为需确认。第四层 OS 沙箱在子进程里隔离执行 shell 命令，限制文件系统访问范围。第五层用户确认弹窗，高风险操作由人拍板。顺序原则是越前置越便宜不经过模型，越后置越精准有上下文可判断。

### Q2. AI 安全评审那一层，模型自己审自己，会不会放水？怎么保证它不误判？

评审用的是独立的小模型，不和主模型共用同一套提示词。评审提示词聚焦安全判断不看业务逻辑，输出只分三类：安全放行、不安全拒绝、不确定升级到确认层。这样避免主模型的业务推理干扰安全判断。另外评审只审工具参数不审执行结果——参数是 Agent 可控的所以必审，结果由 OS 沙箱兜底，不需要模型再评一次。如果评审模型输出格式不符合三类标准，默认按"不确定"升级处理，宁可多弹一次确认也不能漏。

### Q3. OS 沙箱是怎么实现的？

采用的不是虚拟机方案，而是**受限令牌**——利用系统原生的进程降权机制控制写入范围，只允许 Agent 在工作目录、临时目录和专属数据目录内做文件操作，系统目录写不进去。命令执行走独立子进程，环境变量中临时目录和应用数据路径被重定向到沙箱隔离区。另有两道前置防线：命令涉及的文件路径先过目录检查，`rm -rf` 等危险模式在命令黑名单里直接拒绝。核心思路不是信任模型，而是假设命令可能有害、通过多层限制让它做不了坏事。

### 二、上下文压缩

### Q4. Context 快满了怎么办？压缩怎么设计？

在 Pi SDK 原生压缩引擎之上叠加了三层治理。

第一层**工具输出修剪**：压缩前先把旧轮次里大文件读取结果清掉——那些内容当时有用过后就是噪声，清除后既能直接缩小上下文，也让后续压缩质量更高。第二层**缓存保留压缩**：在同一个缓存前缀上生成结构化摘要，按任务、文件、过程三个维度组织——记目标、进度、阻塞点和关键上下文，记改了什么文件，记约束、关键决策和失败原因——外加文件操作清单。因为前缀没变，大模型的缓存可以复用，避免了每次压缩都重新编码整个上下文。第三层**硬截断兜底**，压缩后仍超限走截断防死锁。另加两道保险：1.**防抖计数器**在反复压缩时强制阻断循环；2.压缩后从原始来源重新加载项目规则和记忆，防止摘要代际衰减。

### Q5. 压缩后怎么判断没破坏当前任务？

主要看五个点：压缩后 Agent 还知不知道当前任务是什么、还记不记得改过哪些文件、最近失败的测试和错误原因有没有保留、权限模式有没有被压缩意外改变、项目规则和长期记忆是不是从原始来源重新加载了而不是只靠摘要转述。压缩不是为了变短，而是变短以后还不迷路。

另外还做了一个行为层面的校验测试：压缩前让 AI 每轮回复末尾固定加一句特定指令，压缩后看它是否还能遵守——用实际行为来判断压缩有没有丢失约束，比看一眼生成的总结文本要可靠得多。

### 三、Plan / Compose 工作流

### Q6. Plan 模式和 Compose 工作流是怎么设计的？有什么区别？

Plan 模式和 Compose 解决的是两个不同层面的问题。**Plan 是权限模式**——在工具层限制 Agent 只能读代码、搜文件、跑类型检查这类只读操作，同时设计并开放 Question 提问工具让模型在规划时把模糊需求先问清楚，不能写文件或执行有副作用的命令。模型确认需求后输出结构化计划并创建树形任务清单，用户确认切到操作模式才执行。它的价值是"想清楚了再动手"。

**Compose 是工作流模式**——不限制工具权限，而是基于 Superpowers Skills 模式给模型注入六套结构化技能管道：头脑风暴理清需求、制定实现计划、测试驱动开发、小步执行、代码审查、最终验证，同时开放工作流工具让模型在沙箱里并行派遣子 Agent 处理独立子任务。它的价值是"把复杂迭代约束在可追踪的管道里推进"。

### Q7. 子 Agent 并行执行时，怎么汇总各自的结果？如果有 Agent 失败怎么处理？

Compose 执行阶段用批量派遣子 Agent，各自跑在独立会话里互不干扰。结果由主 Agent 统一收集：成功的按原任务顺序合并输出，失败的不直接崩掉整个管道——主 Agent 拿到子任务的错误栈和已修改文件列表后，判断是否需要重试、降级用简化方案完成、还是跳过该子任务继续。这样单点失败不会让整个迭代中断。

### 四、主动巡检与定时任务

### Q8. Agent 能自己定时醒来干活吗？

做了两套互补的机制。**心跳巡检**——每隔固定时间自动触发，先把工作台文件快照对比出变化，再把变化列表、巡逻日志和长期记忆一起喂给模型，由模型自主判断有没有可主动处理的事，比如用户放了任务指令文件或者工作区有资料需要整理，没有预定义任务列表。**定时调度**——按用户预设的时间表和任务指令执行，每分钟检查有没有到期的，调度逻辑只管到没到时间、到了就执行，模型不参与要不要做的决策。核心区别：心跳是模型自己决定做什么，Cron 是按既定时间表做事。

### Q9. 巡检和正常对话冲突吗？如果用户正在聊天，心跳来了会不会打断？

不会。心跳走的是独立后台会话，不和用户的活跃会话共用对话流。用户聊天时心跳只在文件系统层面做快照比对和变更记录，不触发模型推理；等检测到用户空闲后，才把累积的巡检结果喂给模型做决策。两个通道互不阻塞。

### 五、记忆系统

### Q10. 记忆系统怎么设计？短期长期怎么分工？

短期记忆在单次会话内生效，核心就三块：对话历史本身由框架维护的消息流；**任务树**结构化记录做了什么、正在做什么、什么被阻塞了；以及每十轮、会话结束和每天定时生成的滚动摘要，提取用户画像事实后编译进长期记忆文件。

长期记忆跨会话共享，基于 **SQLite** 存储。每条记忆是一个元事实，比如"用户偏好 TypeScript 严格模式"。由模型从定时构建的滚动摘要中批量提取元事实，带标签存入，检索时用标签匹配加 **FTS5** 全文搜索。产物最终编译成记忆文件按需注入系统提示词，让 Agent 跨会话记住用户偏好。此外还有**置顶记忆、可编辑记忆和记忆开关**——用户发现记错了可以直接在对话里纠正，开关关了就不写入不读取，防止污染。

#### Q10-1. 追问和上下文压缩的摘要的回答
上下文快满时另有一套独立的压缩机制，把早期对话压缩为结构化摘要但保留当前目标、已改文件和失败测试不丢，不经记忆系统。

### Q11. 长期记忆里保存了过时或错误的信息，后续 Agent 一直沿用，怎么防止和纠正？

分源头预防和事后纠正两条线。

源头预防上，不是所有信息都该进长期记忆——临时任务里的文件判断和实现方案不一定是长期事实，我做了**会话级记忆开关**和作用域隔离，用户能控制哪些会话的结论被写入，临时判断不轻易固化。事后纠正上，用户可以直接在对话里通过记忆接口删掉或修正错误记忆，还有置顶记忆机制让关键事实不被淹没。机制层面，每条记忆带来源和时间戳，文件变了旧摘要自动失效；最根本的是**代码事实优先于记忆**——记忆只是提醒"可能相关"，真正改代码前必须读当前文件确认，这样即使记忆错了也不会逐轮放大。

### Q12. 为什么用 SQLite + FTS5 而不是向量数据库？

SQLite 是嵌入式关系数据库，FTS5 是它内置的全文搜索扩展，能高效做关键词匹配。记忆的存入和检索两端都是 LLM 在生成关键词——存入时从对话提取标签写入，检索时根据当前任务生成查询词用全文搜索匹配。两边的用词习惯天然一致，不需要嵌入模型做语义翻译。v1 用向量方案时发现嵌入偏差反而导致召回不准，v2 切到标签匹配后效果没差但去掉了向量模型的依赖和计算成本。本质不是语义相似度搜索，而是模型自己写的标签自己搜。

### 六、通用架构与工程

### Q13. 先整体介绍一下你的本地 Coding Agent 项目，从输入任务到最终修改代码，完整链路是怎样的？

收到任务后分三步：**准备、执行、收敛**。

准备阶段先恢复会话上下文——工作目录、历史对话、权限模式、模型配置、项目规则和相关记忆——然后判任务类型：需求模糊用提问工具先澄清，复杂改动先进 **Plan 只读模式**读代码、拆任务、列风险，用户确认后再切到操作模式执行。执行阶段模型不直接碰文件，而是通过工具层把决策翻译成读文件、搜索代码、编辑、跑测试等动作，每次调用前穿过**权限管道**——Plan 模式只能读，写文件和命令需要对应权限，危险命令直接拒绝。收敛阶段失败不报错退出，错误信息带回下一轮让 Agent 缩小范围重新修复，最终用测试通过、类型检查零错误、人工验收完成闭环。不是一次性撞对，而是**生成→验证→发现问题→带着证据再修→再验证**的收敛循环。

### Q14. 你项目里的工具系统是怎么做的？

一个新工具从定义到被调用，核心解决四件事。

第一是**被发现**：定义工具名、参数结构、功能说明和执行逻辑，说明要写得足够清楚模型才知道什么时候该调用；注册进工具列表后，系统根据当前会话的权限模式和工作流过滤可见工具，不是所有工具永远开放。第二是**安全执行**：模型选择工具后不会直接跑，先穿过权限管道——读文件通常放行，写文件可能需要确认，危险命令直接拦截。第三是**失败反馈**：执行出错时把错误信息写回对话记录，让模型在下一轮知道哪里出了问题、可以怎么调整。第四是**结果回写**：工具的输出作为对话的一部分保留，后续可以引用和追踪。

### Q15. 工具调用失败时，Agent 是直接报错还是做恢复和重试？

关键是区分**可恢复的错误**和**不能绕过的安全边界**，否则重试很容易变成乱试。

可恢复的情况：文件不存在就把错误返回给模型，让它重新搜索路径或者问用户；命令超时保留已有输出，缩小测试范围再跑；测试失败把失败用例和错误栈带回下一轮对话，让模型根据具体错误信息定位修复。不可恢复的情况：权限不够就是安全边界，系统直接硬拦截，弹给用户确认或在只读模式下直接拒绝，不能让模型自己绕过。我的原则就一条：普通错误给模型足够信息让它继续修复，安全错误必须由系统兜底拦截，不能靠模型自觉。

### Q16. 支持不同模型后端吗？怎么抽象请求格式、响应结构、错误码和重试逻辑？

支持。核心思路是把**模型标识和模型服务商分开**——同一个模型名可能来自不同供应商，配置里独立记录服务商、接口地址、密钥、协议和模型能力。接入多家时做一层**适配层统一入口**：上层 Agent 只需要知道"我要发一段对话、有哪些工具可以用、要边生成边返回"，不关心底层是 OpenAI 还是 Anthropic 的格式差异，适配层负责把各家格式转成内部统一结构。错误处理也做标准化分类：网络抖动按指数退避**重试**，上下文超出限制先触发**压缩**，权限相关错误**不重试**必须弹给用户确认或直接拒绝，不让各家 API 的原始错误码往上污染业务逻辑。

### Q17. Agent 反复读同一文件或调同一工具，怎么识别？

从三个层面来看。文件层面，记录最近读过哪些文件以及文件摘要是否变化——如果内容没变，重复读取时可以提醒已有结果。工具层面，记录相近时间段内同一个工具被调用过的参数组合，如果完全重复就提醒避免无效调用。任务层面，用**任务树**结构化记录已经完成什么、正在做什么，减少模型因为忘记进度而去重复操作。

但我不会强行拦截所有重复。比如文件刚被修改后重新读一遍是完全合理的。更好的做法是**提醒加统计**，让 Agent 自己判断要不要跳过，而不是粗暴禁止，否则反而会影响正常的工作流。

### Q18. 评测体系怎么设计？怎么判断改动让 Agent 变强？

做的是轻量评测而不是大规模排行榜，目标不是刷榜，是判断框架改动有没有让 Agent 更稳。

思路是接公开题库——某个公开的编程题本身有测试命令，Agent 负责解题、生成修改，然后跑题目自带的测试来判断过没过。指标分三类：结果指标看通过率和失败原因分布；效率指标看单任务耗时、修改代码量、上下文消耗；过程稳定性指标看工具调用次数、确认弹窗次数、上下文压缩触发次数。判断一次改动是否有效不能只看一个 demo 成功，要在**同一模型、同一批题、同一预算**下对比——通过率更高、失败更少、过程更稳定，才说明框架改进真的生效了。

### Q19. Prompt 调用和 Agent 设计有什么区别？

Prompt 工程解决的是表达问题——把需求说清楚，让模型给一个好答案。这当然重要，但它本质上还是一问一答。

Agent 设计解决的是执行问题。一个真正能落地的 Coding Agent 必须知道任务怎么拆、什么时候该读代码、什么时候该问用户、什么时候该调用工具、工具失败之后怎么恢复、结果怎么验证、哪些操作必须被权限拦截。所以我在项目里没有只堆提示词，而是把这些流程做成系统能力：Plan 模式保证规划阶段不产生副作用，Compose 让复杂任务按管道推进，工具层把模型意图变成可追踪的文件和命令操作，权限沙箱负责拦住高风险动作，测试和公开题库负责判断结果是否真的可用。简单说，Prompt 工程让模型更会说，Agent 工程让模型能按流程做事，并且做错了能被发现和修正。

### Q20. 为什么用 Pi SDK 而不是 LangChain 或 LangGraph？

Pi SDK 是开箱即用的 Agent 运行时——会话管理、工具执行、权限管道、流式推送这些能力已经内置好了，我们可以在这个基础上专注做策略层的设计，比如五种权限模式怎么定义、Plan 和 Compose 怎么编排。LangChain 和 LangGraph 的优势在另一面：它是纯粹的代码框架，你可以精确控制每一步模型调用和状态流转，出问题时调用栈更透明、更容易定位和修复，但执行环境、安全体系、工具注册这些基础设施得自己从零搭建。选型本质上是在"基础设施开箱即用"和"执行链路完全可控"之间做权衡——对我们这个需要快速迭代的本地 Agent 场景，Pi SDK 的集成度更匹配。
