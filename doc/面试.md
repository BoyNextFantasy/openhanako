## 1. 项目介绍

Satori 是一个基于 Pi SDK 构建的桌面端 AI 编程助手，对标 Claude Code / Codex。我负责将 Agent 从零散的工具调用提升为安全可控、有长期记忆、能主动巡检的完整运行体系，包括权限防线、上下文压缩、Plan 模式与工作流编排、定时巡检和记忆系统的设计与验证。

## 2. 面试问答

### Q1. 先整体介绍一下你的本地 Coding Agent 项目，从输入任务到最终修改代码，完整链路是怎样的？

可以把它理解成一个“会自己使用开发工具的 AI 编程助手”。我更关注的是它能不能完成一个闭环，而不是只回答得像开发者。

当系统收到一个任务后，会话引擎会先恢复当前状态，包括工作目录、历史消息、权限模式、模型配置、项目规则和相关记忆。然后 Agent 会判断任务类型：如果需求不清楚，先提问；如果是复杂修改，先拆步骤和风险；如果可以执行，再进入工具调用。

模型不会直接碰本机文件，而是通过工具层读文件、搜索代码、编辑文件、运行测试、维护任务列表。每次工具调用前，权限层都会判断这件事能不能做：比如 Plan 模式只能读代码和整理计划，不能写文件；高风险操作需要用户确认或直接拒绝。

工具结果会实时推送，用户能看到 Agent 读了什么、跑了什么命令、哪里失败了。失败后系统不会只停在报错，而是把错误输出带回下一轮，让 Agent 缩小范围继续修。最终用测试、类型检查或人工验收确认结果，这就是“输入任务 -> 拆步骤 -> 调工具 -> 改代码 -> 跑测试 -> 失败恢复 -> 复审沉淀”的闭环。

### Q2. 你的 Agent 支持不同模型后端吗？如果接入多个模型服务，你会怎么抽象请求格式、响应结构、错误码和重试逻辑？

支持。我的做法是把“模型”和“模型服务商”分开。比如同样叫 `gpt-4.1`，它可能来自不同服务商，所以配置里会记录模型 id、服务商、接口地址、密钥、请求协议和模型能力。

接多个模型服务时，我会做一个统一入口：上层 Agent 只关心“我要发一段对话、这些工具可以用、我要边生成边返回”，不关心底层是 OpenAI 格式、Anthropic 格式还是兼容接口。不同服务商的差异由适配层处理，适配层就是专门把各家格式转成项目内部统一格式的代码。

错误也要统一。比如网络失败、限流、上下文太长、工具格式错误，不能直接把各家 API 的原始错误往上抛。上层只需要知道：这个错误能不能重试，需不需要压缩上下文，需不需要用户处理。网络抖动可以重试；上下文太长应该先压缩；权限错误不能重试，必须让用户确认或直接拒绝。

### Q3. 你项目里的工具系统是怎么做的？比如一个新工具从定义、注册、被 Agent 发现，到最后被调用，完整流程是什么？

一个工具不是简单写一个函数，而是要让模型“看得懂、调得动、出错可恢复、权限可控制”。这也是 Prompt 调用和 Agent 设计的分界：模型不能只会说，还要能通过工具安全地做事。

首先定义工具名、参数、说明和执行逻辑。说明要写清楚，不然模型不知道什么时候该用。然后把它注册进工具列表，但不是所有工具永远开放，系统会根据当前会话、权限模式和工作流决定本轮能看到哪些工具。

模型选择工具后，后端不会马上执行，而是先过权限检查。比如读文件通常可以直接允许，写文件可能需要确认，危险命令会被拒绝。执行完以后，结果会写回会话记录。

所以工具系统解决的是四件事：模型怎么发现工具，工具怎么安全执行，失败信息怎么反馈给模型，执行结果怎么回到对话里。

### Q4. 如果工具调用失败，比如文件不存在、命令超时、权限不够，你的 Agent 是直接报错，还是会做恢复和重试？

我不会所有失败都自动重试。关键是区分“可以恢复的错误”和“不能绕过的边界”，否则 Agent 很容易把重试变成乱试。

比如文件不存在，可以把错误返回给模型，让它重新搜索路径或问用户。命令超时，如果是测试命令，可以保留已有输出，让模型缩小测试范围再跑。测试失败时，要把失败用例和错误栈带回下一轮，让模型定位具体原因。权限不够就不能自己绕过去，因为这是安全边界，必须弹给用户确认，或者在只读/规划模式下直接拒绝。

我的原则是：普通错误要给模型足够信息继续修，安全错误要由系统硬拦截，不能靠模型自觉。这样失败恢复是受控闭环，不是无限重试。

### Q5. 你提到做了多轮任务中的上下文治理，可以举一个真实场景吗？比如代码改到一半上下文越来越长，你是怎么处理的？

一个典型场景是多文件功能迭代。Agent 读了很多文件，跑了多次测试，又产生了一堆错误日志。对话越来越长后，如果不治理上下文，模型很容易忘记最开始的需求、改过哪些文件、哪个测试还没过。

我的处理方式是分层记录。当前几轮对话和工具结果保留在会话里；任务进度放到任务树里；稳定的用户偏好或项目事实才进入长期记忆。上下文快满时，会做上下文压缩，也就是把早期对话整理成摘要。

但压缩时不能随便总结。我会重点保护当前目标、最近失败的测试、已修改文件、关键工具结果和项目规则。压缩后还会重新加载项目规则、技能和记忆，避免越压缩越丢信息。

### Q6. 上下文压缩之后，你怎么判断压缩没有破坏当前任务？有没有什么校验标准？

我主要看几个标准。

第一，压缩后 Agent 还知不知道当前任务是什么。第二，它还记不记得改过哪些文件。第三，最近失败的测试和错误原因有没有保留。第四，权限模式有没有保持，比如规划模式压缩后仍然不能写文件。第五，项目规则和长期记忆有没有重新加载，而不是只靠摘要转述。

简单说，压缩不是为了“变短”而已，而是为了“变短以后还不迷路”。我会用测试去验证这些边界，比如压缩后是否仍保留当前任务、最近工具输出和项目规则。

### Q7. 任务摘要、文件摘要、过程笔记这些压缩产物，你是怎么生成和维护的？如何避免关键信息被压掉？

我不会把所有内容都混成一段“聊天总结”，而是按用途分开。

任务摘要记录目标、当前进度、下一步和阻塞点。文件摘要记录这个文件是干什么的、关键接口是什么、这次改了哪里。过程笔记记录测试结果、失败原因和用户确认过的决定。

避免关键信息被压掉，主要靠三点：摘要格式固定，不让模型随意发挥；最近的上下文优先保留，因为它最影响下一步；项目规则、记忆、技能这类长期内容从原始来源重新加载，不靠一代代摘要传下去。

### Q8. 如果压缩后的摘要里遗漏了关键约束，导致后续 Agent 做错了，你会怎么发现并修正？

发现主要靠三类信号：测试失败、权限拦截、用户可见的计划和任务记录。

如果遗漏的是代码约束，测试会报错；如果遗漏的是“不能动手”这种流程约束，权限层会挡住；如果遗漏的是需求理解，任务树和计划记录能帮助对照发现偏差。

修正时我不会只说“让模型下次注意”。更可靠的是把约束放回源头：补项目规则、补测试，或者把它做成工具层和权限层的硬规则。能系统保证的，就不要只靠一句提示词。

### Q9. 如果长期记忆里保存了过时的文件摘要，后面 Agent 又拿它做判断，这种污染怎么处理？

首先要避免不该记的东西进入长期记忆。某次任务里的文件判断、临时实现方案，不一定是长期事实。Satori 里有会话级记忆开关和作用域隔离，就是为了减少这种污染。

如果已经记错了，要让用户能改。现在有可编辑记忆、置顶记忆、查看记忆、删除记忆，也做了记忆交互接口让用户在对话里直接操作。用户发现错误记忆后，可以直接删除或修正。

更稳的做法是记忆带来源和时间。如果某个文件后来变了，旧摘要就不能当成事实，Agent 应该重新读文件确认。

### Q10. 如果模型把错误结论写进了记忆，比如误判某个函数作用，后续任务一直沿用这个错误，你怎么做纠错？

我会做三件事。

第一，让用户看得到、删得掉。记忆接口就是为了让用户直接纠正错误记忆。

第二，控制记忆范围。临时任务里的判断不要轻易变成长期记忆。

第三，让代码事实优先于记忆。记忆只能提醒“可能相关”，但真正改代码前，Agent 还是应该读当前文件确认。这样即使记忆错了，也不会一直放大错误。

### Q11. 多轮执行中，Agent 可能反复读同一个文件或重复调用同一个工具。你是怎么识别重复状态的？

可以从文件、工具和任务三个层面看。

文件层面，记录最近读过哪些文件、文件有没有变。如果没变，再读时可以提醒已有结果。工具层面，记录同一个工具在相近时间里用过哪些参数，避免重复跑完全一样的只读操作。任务层面，用任务树记录已经做完什么、正在做什么，减少模型忘记进度。

但我不会强行拦截所有重复。比如文件刚被修改后，重新读一遍是合理的。更好的方式是提醒和统计，而不是粗暴禁止。

### Q12. 你怎么看 RAG、Memory 和 Context Engineering？这三者分别解决什么问题？在你的 Coding Agent 里是怎么配合的？

我会这样解释：

RAG 是“需要时去资料库里查东西”，比如查文档、查历史代码。Memory 是“长期记住稳定事实”，比如用户偏好、项目规则、历史决策。Context Engineering 是“本轮到底给模型看什么”，也就是在有限窗口里组织任务、文件、工具结果、记忆和规则。

在 Coding Agent 里，这三者不能混用。RAG 负责找资料，Memory 负责长期事实，Context Engineering 负责把这些信息合理塞进本轮模型输入。最关键的是边界：临时任务状态不能随便变长期记忆，旧记忆也不能替代真实代码。

补充一个实现细节——很多人觉得记忆系统就是向量数据库做语义检索，但这个项目没走向量路线。长期记忆用的是 SQLite + FTS5 全文搜索 + LLM 标签匹配。因为记忆的存入和检索两端都是 LLM 在生成关键词，它的"语言习惯"在两边是天然一致的，不需要 embedding 做中间翻译。v1 用过向量搜索，v2 改成标签检索了，效果没差，但去掉了向量模型的依赖项和计算成本。

### Q13. 你们的记忆系统具体是怎么设计的？短期长期怎么分工？

传统 LLM 每次对话都是"失忆"的，Agent 必须有记忆才能做复杂任务。我们设计了两层：

短期记忆在单次会话内生效。核心就三块：对话历史本身（Pi SDK 维护的消息流）、任务树（结构化记录"做了什么、正在做什么、什么被阻塞了"）、滚动摘要（每 10 轮对话用 LLM 压缩一次，存进会话）。上下文快满时还有自动压缩，把早期对话生成结构化摘要，但保留当前目标、已改文件、失败测试和项目规则不丢。

长期记忆跨会话共享，由 SQLite FactStore 承载。每条记忆是一个"元事实"——比如"用户偏好 TypeScript 严格模式""项目 react-blog 用了 react-router v6"。记忆提取不走实时 embedding，而是在特定时机由 LLM 批量处理：每 10 轮滚动摘要后、session 结束时、每天一次。提取出的元事实带标签存入 FactStore，检索时用标签匹配 + FTS5 全文搜索。

长期记忆的产物最终编译成 `memory.md` 文件，在 system prompt 里注入给模型。另外还有置顶记忆（`pinned.md`）和可编辑记忆——用户看到模型记错了，不用离开对话，直接操作纠正。整条记忆流水线受会话级记忆开关控制，关了就不写入，防止污染。

这个设计不依赖向量数据库。原因是标签——存入和检索两端都是 LLM 在生成，两边用词习惯一致，FTS5 全文搜索就够用，没必要引入 embedding 的额外偏差和计算成本。简单说，不是"语义相似度匹配"，而是"LLM 自己写的标签，LLM 自己搜"。

### Q14. 你对 Agent Harness 怎么理解？它和单纯调用 LLM API 的区别是什么？

单纯调用 LLM API，就是把问题发给模型，再拿回答回来。

Agent Harness 可以理解成“让模型真正干活的一整套运行环境”。它要管理会话、准备上下文、提供工具、执行命令、控制权限、处理错误、保存记忆、展示过程、跑测试。

对 Coding Agent 来说，模型只是大脑，Harness 是身体和工作台。没有 Harness，模型最多给建议；有了 Harness，它才能安全地读代码、改代码、跑测试。

### Q15. 你的 Agent 有没有评测体系？你怎么设计 benchmark、case、指标？怎么判断一次改动真的让 Agent 变强了？

有，但我做的是轻量评测，不是大规模排行榜，目标是判断框架改动有没有让 Agent 更稳，而不是刷榜。

我的思路不是自己出题自己判，而是接公开题库。这里的 benchmark 可以理解成“固定题库 + 固定判断方式”。比如某个公开 coding 题本身有测试命令，Satori 负责让 Agent 解题、生成修改，然后跑题目自带测试来判断过没过。

指标上我会看三类：第一，结果有没有通过，比如通过率和失败原因；第二，效率怎么样，比如耗时、改了多少代码、用了多少上下文；第三，过程稳不稳，比如工具调用次数、确认次数、上下文压缩次数。这些指标都围绕“能不能闭环完成任务”，而不是只看模型回答漂亮不漂亮。

判断一次改动是否让 Agent 变强，不能只看一个 demo 成功，而要在同一模型、同一批题、同一预算下对比。如果通过率更高、失败更少、过程更稳定，才说明框架改进有效。

### Q16. 如果 Agent 在执行代码修改时生成了错误 patch，你怎么做回滚、验证和再尝试？

首先，Agent 默认不会自动提交。错误修改会留在工作区，方便看 diff，也就是查看这次到底改了哪些代码，然后再跑测试。

发现 patch，也就是代码补丁错了，我会先跑相关测试或类型检查，拿到明确失败原因。然后看 diff，判断是需求理解错、实现错，还是误改了无关文件。修复时尽量最小改动，不扩大范围。

如果要回滚，也不会直接 `git reset --hard`，因为工作区可能有用户自己的改动。更安全的是按文件或按 patch 精确回退。重新尝试时，我会把失败测试、错误原因和已改文件明确告诉 Agent，再让它重新规划局部修复。这里其实就是一个小的 loop engineering：生成、验证、发现问题、带着证据再修一轮，直到测试通过或确认方案方向错了。

### Q17. 你平时用什么 AI？一个需求给到你，你通常怎么用 AI 辅助完成开发？

我不会把 AI 当成“一句话生成代码”的工具，而是把它当成一个需要被管理的开发协作者。真正重要的不是用哪个模型，而是我怎么给它提供项目地图、边界和验收方式。

我会先维护一份高质量的 `AGENTS.md` 作为入口文件，告诉 Agent：代码入口在哪里、核心模块怎么分、测试怎么跑、迭代文档写到哪里、Git 和安全规则是什么。它不是塞满所有细节的大文档，而是一张地图，让 Agent 需要信息时知道去哪里取，该沉淀结论时知道写到哪里。

一个需求进来后，我不会一开始就写一大堆永远不变的规格文档。我的经验是，很多约束是从读代码、试方案、跑测试的碰撞里长出来的。前期更适合用 Plan 模式让 Agent 先读代码、问问题、拆任务但不动手；复杂迭代再用 Compose / Superpower Skills 这类流程，把它约束在 brainstorm、plan、execute、review、verify 的节奏里。这个过程也可以叫 loop engineering，简单说就是让 AI 在“规划-生成-审查-修改-验证”的循环里不断收敛，而不是一次性赌它全做对。等某个规则真的稳定了，再沉淀成文档或测试，避免反复摇摆。

同时我会非常重视项目解耦和模块化。AI 的注意力有限，项目大了以后容易拆东墙补西墙，所以架构上要让它一次只处理一个边界清晰的模块，改 A 尽量不影响 B。最后一定用 Git、单元测试、类型检查、冒烟测试这些手段兜底。AI 可以帮我加速读代码、拆方案、写实现、补测试和复审，但最终有没有做对，要靠可运行的验证结果说话。

### Q18. 你在使用 AI 的过程中，会怎么拆需求、读代码、让模型改代码、跑测试和 review 结果？

我的流程不是“提需求 -> 等 AI 写完 -> 看运气”，而是一个带审查和验证的循环。

第一步是拆需求。我会先判断这是 bug、功能、架构调整还是文档工作，再写清楚验收标准。这个阶段我会让 AI 先读入口文件、`AGENTS.md`、相关迭代文档和代码调用链，不让它凭空猜。如果需求还模糊，就让它用 question 工具或直接列问题，先把关键不确定点问清楚。

第二步是定计划。简单任务直接写短计划；复杂任务用 Plan 模式，只允许读代码、拆任务、列风险，不允许直接改文件。计划通过后再进入执行阶段。多文件迭代我会开 Compose，让它按 brainstorm、plan、execute、review、verify 的节奏走，也就是先碰撞出方案，再逐步形成稳定约束。

第三步是小步实现。让 AI 一次只改边界清楚的模块，改 A 就尽量不碰 B；每一轮都看 diff，也就是这次具体改了什么，再跑对应测试或类型检查。失败了就把失败信息喂回去，让它重新定位，而不是继续扩大修改范围。

第四步是复审和沉淀。我会让 AI 或新会话扮演审查者，看有没有漏文件、漏测试、误改、越权等问题。通过后，把真正稳定的规则沉淀到 `AGENTS.md`、迭代文档或测试里；不稳定的想法先不写成死规格。对我来说，好的 AI 开发流程不是提前写一堆大而全的文档，而是通过一轮轮计划、实现、审查、验证，把项目约束从代码和测试里长出来。

### Q19. Prompt 调用和 Agent 设计有什么区别？为什么你的项目不是普通 Prompt 工程？

Prompt 调用更像“把需求说清楚，让模型给一个答案”。这当然重要，但它主要解决表达问题。

Agent 设计解决的是执行问题。一个真正能落地的 Coding Agent，要知道任务怎么拆、什么时候读代码、什么时候问用户、什么时候调用工具、工具失败后怎么恢复、结果怎么验证、哪些操作必须被权限拦住。

所以我做 Satori 时没有只堆提示词，而是把这些流程做成系统能力：Plan 模式保证规划阶段不产生副作用，Compose 让复杂任务按固定流程推进，工具层负责把模型意图变成可追踪的文件/命令操作，权限沙箱负责拦住高风险动作，测试和公开题库负责判断结果是否真的可用。

简单说，Prompt 工程让模型“更会说”，Agent 工程要让模型“能按流程做事，并且做错了能被发现和修正”。这也是我项目里最想体现的能力。

### Q20. 这个项目有插件系统吗？插件能做什么？

有，不过插件系统不是我负责的部分。据我了解，它的架构是约定优先——插件是一个文件夹，`hana.json` 声明身份和权限等级，然后按目录约定贡献能力：`tools/` 放工具、`routes/` 放 API 路由、`skills/` 放技能、`extensions/` 放扩展代码、`agents/` 放 Agent 模板、`providers/` 放 LLM 提供商。

插件有 `full-access` 和 `restricted` 两级权限。restricted 插件只能贡献工具和命令，不能接触核心引擎——这点很重要，因为插件是第三方写的，不能让它随便碰到引擎内部。还有一点值得说的是，插件贡献的工具不是独立运行的——它们会被 Satori 的权限系统统一包裹，和内置工具走同一套安检管道。也就是说，用户不会因为装了插件就开了一个安全后门。

### Q21. Pi SDK 自带的扩展系统和 Satori 的插件系统有什么区别？

这两个概念名字不一样，其实说的是两个层次的东西。

Pi SDK 有一套叫 Extension 的机制——本质是钩子，可以写一段 TypeScript 文件，监听会话事件、注册工具、弹 UI 对话框。它很灵活，但没有打包格式和分发机制，就是一个代码片段。

Satori 在 Extension 之上包了一层"应用商店"框架。解决的是三个问题：一是分发——插件有标准的 `hana.json` + 目录结构，可以打包成 zip 拖拽安装；二是安全——Pi SDK Extension 是裸代码没有权限限制，Satori 给插件加了信任分级和权限包裹；三是生态——插件可以有市场分发、多语言描述、贡献 Agent 模板和 LLM 提供商。

底层是通的——Satori 插件的扩展代码最终也是通过 Pi SDK 的 `extensionFactories` 加载运行的，所以 Pi 生态的扩展能力 Satori 都能承接，只是中间加了一层包装保证安全和可分发。

我虽然没直接做插件系统的迭代，但因为要做工具层和权限层的工作，必须理解插件的工具怎么注册、怎么被安检包裹、怎么跟内置工具共存，所以这些概念我很清楚。

### Q22. Agent 大多数时候是等用户给指令才行动的，你的项目里有没有让 Agent 自己"定时醒来干活"的机制？

有，做了两套互补的机制——心跳巡检（Heartbeat）和 Cron 定时调度。

心跳巡检是让 Agent 从被动应答变成主动行动的核心。每隔固定时间（默认 31 分钟），系统不依赖用户发消息，自己触发一轮巡检：先做工作台文件快照对比，算出新增/修改/删除的文件变化，再把变化列表、近期巡检记录、长期记忆一起喂给 Agent。Agent 独立判断有没有可主动处理的事——比如用户放了新的任务指令文件、工作区有文件改动需要整理、或者有值得学习的资料。判断后直接调用工具执行，不需要用户在场。

Cron 定时调度是另一条线，更偏"按时间表执行"。每分钟检查一次有无到期的定时任务，到期就驱动 Agent 在后台执行，支持超时自动中止和失败退避重试。调度逻辑本身不经过 LLM，只有到了执行时才创建独立 session 跑任务。

两点分工很明确：心跳是"Agent 自己决定要做点什么"，Cron 是"按用户设定的时间表执行"。合在一起，Agent 就不再只是等消息的聊天窗口，而是一个能周期性自主工作的后台进程。
