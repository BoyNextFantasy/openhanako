## 1. 项目介绍

Satori 是一个基于 Pi SDK 构建的本地 Coding Agent，对标 Claude Code / Codex，提供桌面端应用。核心要解决的问题是，一个 Agent 不能只会调工具——它需要安全地操作本地文件、具备规划能力并针对模糊问题会调工具询问，在多轮长对话中不迷失方向、记住跨会话的经验和偏好、甚至在没有用户消息时主动巡检工作区。我负责设计和实现了支撑这套能力的五个核心子系统：**权限防线**、**上下文管理**、**Plan模式 / Compose 工作流**、**主动巡检与定时任务**、**记忆系统**。

## 2. 面试问答

### 一、权限防线

### Q1. ⭐ 5 层防线具体每层做什么？为什么是这个顺序？

第一层硬编码命令拦截在最外层直接拒绝危险命令，比如 `rm -rf`，不需要经过模型判断。第二层会话级权限判定根据当前权限模式过滤可用工具。第三层 AI 安全评审用独立的评审模型审操作意图，风险未知的标记为需确认。第四层 OS 沙箱通过受限令牌降权，在子进程里隔离执行 shell 命令，限制文件系统访问范围。第五层用户确认弹窗，高风险操作由人拍板。顺序原则是越前置越便宜不经过模型，越后置掌握的信息越多拦截越精准但成本高。

> ⚠️ 注意：第三层 AI 安全评审仅 AUTO 模式下触发

### Q2. AI 安全评审那一层，模型自己审自己，会不会放水？怎么保证它不误判？

评审用的是独立的评审模型，不和主模型共用同一套提示词。评审提示词聚焦安全判断不看业务逻辑，输出只分三类：安全放行、不安全拒绝、不确定升级到确认层。这样避免主模型的业务推理干扰安全判断。另外评审只审工具参数不审执行结果——参数是 Agent 可控的所以必审，结果由 OS 沙箱兜底，不需要模型再评一次。如果评审模型输出格式不符合三类标准，默认按"不确定"升级处理，宁可多弹一次确认也不能漏。

### Q3. ⭐ OS 沙箱是怎么实现的？为什么不用虚拟机？

不用虚拟机——每条命令都开一台虚拟机，启动延迟和资源开销撑不住。用的是**受限令牌**：系统原生的进程降权机制，开销远低于虚拟机。利用它控制写入范围，只允许 Agent 在工作目录、临时目录内做文件操作，系统目录写不进去；命令执行走降权后的独立子进程。另有两道前置防线：命令涉及的文件路径先过目录检查，`rm -rf` 等危险模式在命令黑名单里直接拒绝。核心思路不是信任模型，而是假设命令可能有害、通过多层限制让它做不了坏事。

> 平台口径：Windows 上是受限令牌，macOS 和 Linux 上各有对应的系统级沙箱机制，思路一致——降权 + 限定可写范围。

### 二、上下文压缩

### Q4. ⭐ 长对话里 Agent 会"翻脸不认账"——20 轮前定的规则后来不认了，还把用户偏好忘了。这个问题你是怎么定位和解决的？

定位：现象是多次压缩之后 Agent 开始违反项目规则。顺着压缩链路查根因——压缩是让模型把旧对话总结成摘要，多次压缩就是"摘要的摘要"，项目规则、用户偏好这些约束两三轮下来就被压没了；它们只以"二手转述"的形式存在于摘要里，这就是代际衰减。

解决是一套分层方案。**第一刀砍在根因上**：持久的东西根本不进摘要池——每次压缩完成后，系统直接从磁盘重读项目规则、记忆文件的原文，重算系统指令写回去；摘要只负责对话历史，规则永远是原文。为什么不从摘要里恢复而要重读原文？摘要天然会丢信息，磁盘原文是零损耗的唯一可信源。**第二层省钱**：压缩前先免费清掉旧轮次的大文件读取结果（保护最近 2 轮不动、错误信息保留），能省够就不调模型——清理是零成本的，调模型做摘要才花钱。**第三层兜底**：如果生成摘要的请求本身就要超窗口，不调模型直接硬截断，保留最近的完整对话；再加防抖——压缩完还是满就计数，连续 3 次直接报错停住，因为那是内容物理上塞不进去，继续压就是死循环。

验收：压缩修复轮的回归验证共 137 个用例通过；端到端是项目规则里写"所有回复必须以 Roger. 结尾"，聊 20 轮以上触发多次压缩，约束依然生效——这就是规则没被摘要吃掉的直接证据。

[追问]

> 上线前被复审抓过什么 bug？

两个印象深的。一是修剪算法误删当前轮：消息里不足两个完整用户轮时，"保护最近 2 轮"的边界找不对，把用户刚读的大文件也剪了——修复是边界找不到就整体不剪，宁可少省不误删。二是扩展注册顺序：清理扩展必须注册在压缩守卫之前，守卫才能看到清理后的数据；最初顺序反了，等于白清。都是子 Agent 交叉复审抓出来的，所以我坚持复审是流程而不是可选项。

> 摘要的格式为什么是结构化的？

固定六节：目标、约束与偏好、进展（完成/进行中/阻塞）、关键决策、下一步、关键上下文；另外代码再拼上读过哪些文件、改过哪些文件两个清单。自然语言摘要不可控，固定模板漏项一眼能看出来，文件清单不靠模型自觉、由代码直接附加。

### Q4-1. 上下文压缩什么时候触发？

两类入口。手动：`/compact` 命令即时触发。自动：给压缩留了约 1.6 万 token 的安全余量，当前用量一旦越过"窗口上限减去余量"这条线就自动压缩——注意这是**绝对余量**，不是百分比水位线，余量大小可配置。此外还有几个间接触发点：切换模型前先压缩适配目标窗口、每天一次定时"翻新"长会话（用当天最新配置整体重建指令再压缩）。

### 三、Plan / Compose 工作流

### Q5. ⭐ Plan 模式和 Compose 工作流是怎么设计的？有什么区别？

Plan 模式和 Compose 解决的是两个不同层面的问题。**Plan 是权限模式**——在工具层限制 Agent 只能读代码、搜文件、跑类型检查这类只读操作，同时设计并开放 Question 提问工具让模型在规划时把模糊需求先问清楚，不能写文件或执行有副作用的命令。模型确认需求后输出结构化计划——有固定字段和必填校验的协议，漏了范围、风险、验收标准这类关键块会被校验拦下——并创建树形任务清单，用户确认切到操作模式才执行。它的价值是"想清楚了再动手"。

**Compose 是工作流模式**——不限制工具权限，而是基于 Superpowers Skills 模式给模型注入六套结构化技能管道：头脑风暴理清需求、制定实现计划、测试驱动开发、小步执行、代码审查、最终验证，同时可在沙箱里并行派遣子 Agent 处理独立子任务。它的价值是"把复杂迭代约束在可追踪的管道里推进"。

[追问]

> 为什么不把 Compose 做成第六个权限模式，或者做成一个新助手？

权限回答"能不能做"，工作流回答"怎么做"，合成一个就表达不出"自动执行+结构化流程""人工审批+结构化流程"这些自然组合；做成新助手则把"用哪个助手"和"用哪种工作流"绑死。所以它是会话级开关，和权限正交，两个维度自由组合。

### Q5-1. 多 Agent 怎么协作？怎么避免互相干扰？

Compose 下可并行派遣子 Agent 处理独立任务，两个关键机制：**共享任务树**——子 Agent 读写同一棵树，各自认领节点，主 Agent 通过树的状态聚合进度，避免重复劳动；**权限隔离**——子 Agent 权限永远不能超过父会话，固定边界高于一切权限模式，防止子 Agent 自递归、写长期记忆、对外副作用。会话间隔离靠独立子会话：每个子 Agent 跑在自己的隔离子会话里，互不持有对方状态。

### 四、主动巡检与定时任务

### Q6. ⭐ Agent 能自己定时醒来干活吗？

做了两套互补的机制。**心跳巡检**——默认每 31 分钟一轮（可按助手配置），先把工作台文件快照对比出变化，再把变化日志和长期记忆一起喂给模型，由模型自主判断有没有可主动处理的事，比如用户放了任务指令文件或者工作区有资料需要整理；任务指令文件（笺）每轮巡检都会检查，有内容就交给模型自主决定要不要行动，执行后重新落指纹，防止模型把自己写的产出当成新任务。**定时调度**——按用户预设的时间表和任务指令执行，每分钟检查有没有到期的，到了就执行，模型不参与要不要做的决策。核心区别：心跳是模型自己决定做什么，Cron 是按既定时间表做事。

### Q7. 巡检和正常对话冲突吗？如果用户正在聊天，心跳来了会不会打断？

不会。心跳走**独立后台会话**——单独的会话目录、后台优先级运行，结果写进活动日志，完全不进用户的对话流，两条通道互不阻塞。心跳的提示词里也明确声明"用户当前没有在跟你对话"，模型不会把巡检上下文当作用户提问。任务指令文件（笺）每轮心跳都会检查、由模型自主判断要不要行动；执行后重新落指纹防自激——防止模型把自己写的日志当成新任务；另有单轮 5 分钟超时兜底。

### 五、记忆系统

### Q8. ⭐ 记忆系统怎么设计？短期长期怎么分工？

短期记忆在单次会话内生效，核心就三块：对话历史本身由框架维护的消息流；**任务树**结构化记录做了什么、正在做什么、什么被阻塞了；以及每十轮、会话结束和每天定时生成的滚动摘要，提取用户画像事实后编译进长期记忆文件。

长期记忆跨会话共享，基于 **SQLite** 存储。每条记忆是一个元事实，比如"用户偏好xxx"。由模型从定时构建的滚动摘要中批量提取元事实，带标签存入，检索时用标签匹配加 **FTS5** 全文搜索。产物最终编译成记忆文件按需注入系统提示词，让 Agent 跨会话记住用户偏好。此外还有**置顶记忆、可编辑记忆和记忆开关**——用户发现记错了可以直接在对话里纠正，开关关了就不写入不读取，防止污染。

#### Q8-1. 记忆的滚动摘要和上下文压缩的摘要是一回事吗？

不是，两套独立机制。压缩摘要服务于**上下文窗口**——快满时把早期对话压成结构化摘要腾空间，保留当前目标、已改文件和失败测试不丢，不经记忆系统；滚动摘要服务于**长期记忆**——每 10 轮沉淀会话事实，走每日管线入库。一个是空间问题，一个是时间问题。

#### Q8-2. 长期记忆按需检索召回吗？什么情况下需要检索？

两条路径。被动注入——每次会话启动时直接注入进系统提示词，Agent 不做任何操作就能看到近期记忆。主动检索工具供模型按需调用，当模型判断当前任务可能涉及历史事实时才触发，用 LLM 生成的标签加 FTS5 关键词去SQLite搜索，不是每次都搜。

#### Q8-3. 长短期记忆是同时注入吗？

是。两者共存于每次对话的上下文窗口——长期记忆在系统提示词里作固定前缀，短期记忆在消息流里随对话增长。

#### Q8-4. 置顶记忆是如何实现置顶的？和长期记忆如何区分开？

普通记忆走自动管线：滚动摘要提取→SQLite→定期合并注入提示词，容量有限可能丢失低频记忆。置顶记忆走独立存储：可以是工具直接写入的独立文件，全程不经过数据库、不截断、不参与合并；自动管线生成的记忆也能被用户选择置顶到这个独立文件。两者在提示词里分层摆放，置顶记忆排在长期记忆上方，标记为用户要求始终保留，不受管线容量影响。

### Q9. ⭐ 有没有一次选型是上线后推翻重来的？

有，记忆检索。这套系统第一版用向量方案：存的时候算嵌入、查的时候算相似度。上线实测发现召回不准，复盘想通了一层——这个场景里存和查的两端都是大模型在写关键词：存入时是模型给事实打标签，检索时是模型生成查询词，两边用词习惯天然一致，中间再塞一个向量模型做"语义翻译"是多余的，翻译偏了反而召回错。第二版改成标签精确匹配优先、全文检索补充，效果没差，砍掉了向量模型的依赖和计算成本。本质不是语义相似度搜索，是模型自己写的标签自己搜。中文检索还有一个专门的坑：全文检索的默认分词不认中文，靠两三字组合展开解决，这块有专项测试兜底。

### 六、通用架构与工程

### Q10. ⭐ 先整体介绍一下你的本地 Coding Agent 项目，从输入任务到最终修改代码，完整链路是怎样的？

收到任务后分三步：**准备、执行、收敛**。

准备阶段先恢复会话上下文——工作目录、历史对话、权限模式、模型配置、项目规则和相关记忆——然后判任务类型：需求模糊用提问工具先澄清，复杂改动先进 **Plan 只读模式**读代码、拆任务、列风险，用户确认后再切到操作模式执行。执行阶段模型不直接碰文件，而是通过工具层把决策翻译成读文件、搜索代码、编辑、跑测试等动作，每次调用前穿过**权限管道**——Plan 模式只能读，写文件和命令需要对应权限，危险命令直接拒绝。收敛阶段失败不报错退出，错误信息带回下一轮让 Agent 缩小范围重新修复，最终用测试通过、类型检查零错误、人工验收完成闭环。不是一次性撞对，而是**生成→验证→发现问题→带着证据再修→再验证**的收敛循环。

### Q11. ⭐ 你项目里的工具系统是怎么做的？

遵循 Pi SDK 的 工具定义规范。底层由 Pi SDK 转发为模型厂商的工具调用格式。在此基础上工具系统解决四件事：按权限模式和工作流过滤可见工具、失败信息带回下一轮、结果回写对话记录。设计上有两个关键理念——一是按当前会话模式动态控制工具可见范围（如规划模式下只见只读工具），只暴露必要的工具描述；二是把工具描述当一等公民对待，描述质量直接决定模型的调用准确率。

### Q11-1. 工具你会用 MCP 吗？还是自己写？大模型工具实现有什么好处？

MCP 是工具/数据源的标准协议，解决工具跨模型、跨 Agent 复用；Function Calling 是模型↔工具的协议。我项目里底层用 Pi SDK 的工具定义规范，内部工具都是自己写的（文件读写、命令执行、搜索、记忆检索），因为内部工具要深度绑定权限、沙箱、审计。好处是结构化 schema——工具名、描述、参数 schema 让模型学会"什么时候调、怎么调"，工具描述质量直接决定调用准确率，所以我把工具描述当一等公民对待。MCP 的价值在生态接入，自己写工具的价值在深度控制。

### Q12. 工具调用失败时，Agent 是直接报错还是做恢复和重试？

关键是区分**可恢复的错误**和**不能绕过的安全边界**，否则重试很容易变成乱试。

可恢复的情况：文件不存在就把错误返回给模型，让它重新搜索路径或者问用户；命令超时保留已有输出，缩小测试范围再跑；测试失败把失败用例和错误栈带回下一轮对话，让模型根据具体错误信息定位修复。不可恢复的情况：权限不够就是安全边界，系统直接硬拦截，弹给用户确认或在只读模式下直接拒绝，不能让模型自己绕过。我的原则就一条：普通错误给模型足够信息让它继续修复，安全错误必须由系统兜底拦截，不能靠模型自觉。

### Q13. ⭐ 支持不同模型后端吗？怎么抽象请求格式、响应结构、错误码和重试逻辑？

支持。核心思路是把**模型标识和模型服务商分开**——同一个模型名可能来自不同供应商，配置里独立记录密钥，模型能力等。利用pi-sdk能力，接入多家时做一层**适配层统一入口**：上层 Agent 只需要知道"我要发一段对话、有哪些工具可以用、要边生成边返回"，不关心底层是 OpenAI 还是 Anthropic 的格式差异，适配层负责把各家格式转成内部统一结构。

### Q14. Agent 反复读同一文件或调同一工具，怎么识别？

从三个层面来看。文件层面，记录最近读过哪些文件以及文件摘要是否变化——如果内容没变，重复读取时可以提醒已有结果。工具层面，记录相近时间段内同一个工具被调用过的参数组合，如果完全重复就提醒避免无效调用。任务层面，用**任务树**结构化记录已经完成什么、正在做什么，减少模型因为忘记进度而去重复操作。

但我不会强行拦截所有重复。比如文件刚被修改后重新读一遍是完全合理的。更好的做法是**提醒加统计**，让 Agent 自己判断要不要跳过，而不是粗暴禁止，否则反而会影响正常的工作流。

### Q15. ⭐ 评测体系怎么设计？怎么判断改动让 Agent 变强？

做的是轻量评测，核心原则是**不自判——让第三方当裁判**。接公开编程题库（Aider Polyglot），题目自带的测试命令是唯一判题权威，我的评测系统只做四件事：拷贝隔离环境、把题面交给 Agent 解题、跑题目自带的测试、记录结果，一行判分逻辑都不写。

单题通过的标准是**三个退出码全零**：装依赖成功、Agent 正常退出、题目测试通过，缺一不可——装依赖失败直接判负不调模型（省成本），Agent 异常退出时测试碰巧能过也不算通过（防假阳性）。指标记录通过与否、耗时、改动文件数；token 类指标预留了字段还没接，如实说。

工程上修过一批影响评测可信度的坑：复用输出目录会被上一轮的代码污染（改为每任务先清空）、超时只杀外层进程留孤儿进程（改按进程树杀）、验收抢在 Agent 写完文件之前（改为等会话真正结束再判题）——这些是子 Agent 交叉复审抓出来的九个问题里的代表。

真实跑分：公开题库的 JavaScript 题，题目自带测试判定通过，109 秒，改 1 个文件。如实表述边界：这是单题轻量验收，证明"公开题库闭环真实跑通、Agent 在第三方判题下通过"，不是榜单分数。

判断"改动让 Agent 变强"用**控制变量**：一次只改一个环节，同一批任务、同一模型，对比通过率和耗时。

### Q16. 为什么用 Pi SDK 而不是 LangChain 或 LangGraph？

Pi SDK 是开箱即用的 Agent 运行时——会话管理、工具执行、权限管道、流式推送这些能力已经内置好了，我们可以在这个基础上专注做策略层的设计，比如五种权限模式怎么定义、Plan 和 Compose 怎么编排。LangChain/手搓的优势在另一面：你可以精确控制每一步模型调用，出问题时调用栈更透明、更容易定位和修复，基础设施得自己从零搭建。选型本质上是在"基础设施开箱即用"和"执行链路完全可控"之间做权衡——对我们这个需要快速迭代的本地 Agent 场景，Pi SDK 的集成度更匹配。

### Q17. task 工具和任务树是干什么的？

任务树是模型可见的树形工作项清单：自动层级编号（T1、T1.1 式），五个状态（待办/进行中/阻塞/完成/放弃），九种操作（创建/查询/开始/阻塞/解除/完成/放弃/改名等），落盘为 JSON 文件、原子写入，跨轮次跨重启不丢。Plan 模式下用它登记计划步骤（只建不启动），切到操作模式后逐个推进；子 Agent 读写同一棵树实现协作分工。模型需要时查树对齐进度，不必把整个清单常驻上下文；后台子 Agent 的进度则通过事件流实时推给前端，用户能看到。

### 七、项目定位与 AI 协作开发

### Q18. ⭐ 这个项目是基于开源项目改的吧？你自己的工作在哪里？

坦然承认基座，然后给证据链。是——我选了成熟的开源 Agent 框架做基座做深度二次开发，这和公司里接手成熟代码库做产品化是同一种工程场景。我自己的工作有三类证据：一是 git 上 107 个定制提交——7 月集中交付了规划模式两代、Compose 工作流、任务树、提问工具、压缩三层治理、对话内记忆动作、公开题库评测接入；二是 12 篇迭代文档，每个特性从问题分析、参考实现对比、设计取舍到测试策略全程留痕；三是回归测试，比如压缩修复轮 137 个用例通过（压缩专项约 80 个）。框架给我的是地基（会话管理、工具执行管线、多模型接入），安全、压缩、工作流这些**策略层**是我的。

> 被追问"哪些是框架自带的"：如实分界——会话管理、工具管线、多模型接入是框架的；我在其上叠的是策略层：什么时候压、压什么、权限怎么分层；记忆侧我做的是对话内的记忆动作和集成验证。分得清基座和增值，比含糊其辞可信得多。

### Q19. ⭐ 代码大量是 AI 写的，那你的价值是什么？

AI 是执行者，我做工程判断，具体四件事：**需求定义**——把"Agent 会忘规则"这种现象翻译成"压缩后从磁盘重读系统指令"这样的技术问题；**方案评审**——AI 给的方案要对比业界做法再拍板，比如压缩修剪的保护参数就是对照 OpenCode 的设计定的；**验收标准**——每轮迭代先写失败测试，"完成"的定义是测试变绿，不是 AI 说做完了；**踩坑判断**——按钮无反应那类问题，AI 会顺着前端一路修，是我判断出该直接验证后端进程里有没有这个路由。反过来说，正因为代码是 AI 写的，验收和复审才必须更严——子 Agent 交叉复审就是被这个现实逼出来的制度。

### Q20. ⭐ 你具体怎么用大模型开发的？说说工作流。

五步闭环：**一，计划文档先行**——目标、现状、逐文件改动、边界与坑、验收命令，这份文档是模型间协作的唯一接口，中途换模型执行也不丢上下文；**二，先写失败测试**——让"做完"有客观定义；**三，AI 按计划实现**，我逐段评审；**四，派独立的 AI 实例做交叉复审**，重点查漏改调用点、跨模块影响——复审真的抓得出问题：压缩那轮 4 个、评测那轮 9 个边界缺陷；**五，验收命令链**——类型检查零错误 → 相关单测 → 全量测试不引入新失败 → 前端构建 → 起服务实测。这套流程本身就是我在项目里沉淀的"AI 协作工程化"。

### Q21. 怎么验收 AI 产出的成果？怎么知道它没胡写？

原则一句话：**验收权威必须独立于生成方**。分三层：代码层——测试、类型检查、编译，这些不是 AI 自己说了算的；行为层——端到端场景验收，比如项目规则里写"回复必须以 Roger. 结尾"，聊 20 轮触发多次压缩，看约束还在不在；能力层——公开题库评测，题目自带的测试当裁判。另外我特别防"测试永远绿灯"这种隐性失效，专门留了失败链路回归（评测的空转模式专门验证"该失败时确实失败"）。

### Q22. 上游官方项目一直在更新，你的分支怎么跟进？

做过一次完整的分叉分析：我的分支和上游已双向分叉——上游领先约 700 个提交（7 月单月就有 500 个，8 月前三周又约 175 个），本地有 107 个定制提交，直接合并的冲突成本和回归风险不可控。所以策略是**选择性吸收**：定期看上游改动清单，按"与本地定制的冲突面、价值、移植成本"三个维度评估候选——比如评估过上游近月的四个大特性（文件历史快照、即时压缩模式、记忆整理、连接器治理），结论是参考设计、按需重实现，而不是直接搬代码。判断标准一句话：**合并的成本低于重实现才合并，否则参考着重做**。分叉点、双向提交数、候选评估都有文档记录。

## 3. 场景题专区

> 面试官现在倾向用"现实开发中遇到的问题"来提问，这些场景题从具体情境切入，考查你把系统设计落到真实问题上的能力。回答套路：先给判断和处理思路，再展开系统里哪套机制在兜底，最后接得住追问。

### S1. 长会话失忆

**场景**：用户开了一个 40 轮的长会话。前 20 轮让 Agent 重构了某个模块并改了好几个文件，后 20 轮换了任务。现在用户问"之前重构时那个接口为什么改成回调了？"，Agent 有点答不上来。你会怎么处理？

**思路**：三层机制兜底，Agent 不会真的失忆。第一，**任务树**——结构化记录做了什么、正在做什么、被什么阻塞，跨轮次持久化不丢失，翻任务树就能对齐当时的进度。第二，**上下文压缩摘要**——六节结构化格式（目标、约束、进展、决策、下一步、关键上下文）加代码附加的文件操作清单，明确记录"改了什么文件"，压缩后这些上下文仍保留。第三，**工具层**——代码事实优先于记忆，Agent 可以直接重新读目标文件拿最新事实，重复读取还有内容摘要变化检测提醒。

[追问]

> 压缩把细节丢了怎么办？

摘要代际衰减问题专门修复过：压缩后从原始来源重新加载项目规则和记忆；涉及代码的事实直接从代码重新读，不依赖摘要记忆。

### S2. 被提示词诱导执行危险命令

**场景**：用户（或一段精心构造的提示词）诱导 Agent 执行强制推送这种危险操作，比如 `git push origin main --force`，或者 `bash -c "git push -f"` 这种包装形式。系统怎么反应？

**思路**：第一层硬编码拦截直接拒绝，不经过 AI 评审也不弹确认——这类危险变体在白名单之外。破坏性命令（比如递归删除文件）和强制推送的危险变体全部直接拦截；命令解析器按引号和转义拆词后，再对词元做黑名单与危险模式匹配，防止简单包装绕过。拦截后返回结构化错误给模型，模型拿到的信息是"该操作被安全策略拒绝"。

[追问]

> 用户真的想强制推送怎么办？

拦截的是 Agent 工具层的行为，用户可以在自己的终端操作；这是设计取舍：宁可误拦不可漏拦，Agent 不提供危险路径。

> 怎么识别包装过的命令？

命令先经解析器按引号、转义拆成词元，再逐词做黑名单和危险模式匹配——不信任模型自报的命令。

### S3. 子 Agent 并发改同一文件

**场景**：Compose 工作流派了两个子 Agent 并行干活，一个在改 a.ts，另一个也要动 a.ts，或者两个都要改配置文件。会不会互相覆盖、把文件写坏？

**思路**：三层防护。第一，**任务划分**——共享任务树让子 Agent 各自认领节点，主 Agent 按树聚合，设计上尽量让改动面不重叠。第二，**独立隔离子会话**——每个子 Agent 跑在自己的隔离会话里，不持有引擎级共享状态，互不干扰。第三，**文件级原子写**——真出现同文件竞争时，写入是原子的，不会产生半个文件；一致性由文件系统保证。

[追问]

> 子 Agent 的权限边界？

永远不能超过父会话，固定黑名单防止它自己再造子任务、防止往长期记忆里乱写，这个边界改不了。

### S4. 面试官看了仓库："这是开源项目吧，你怎么证明你的工作？"

**场景**：面试官打开 GitHub 仓库或让你现场展示，指出项目基于开源框架。如何回应？

**思路**：不回避基座事实，把叙事落在"策略层是我的 + 过程全程留痕"，给三类可现场翻的证据——git 提交历史（7 月密集的定制提交线）、12 篇迭代文档（核心几篇有完整的问题分析、参考实现对比、设计取舍、测试策略）、对应模块的回归测试（压缩修复轮 137 个用例等）。一句话定调："基座是框架的，这个 Agent 为什么安全、什么时候压缩、怎么记住用户，这些策略是我的，而且每一步都有文档和测试。"

[追问]

> 这些文档也是 AI 写的吧？

开发过程和 AI 协作沉淀的，但每个决策——为什么选这个方案、为什么放弃那个——是我拍板的；文档里"参考实现对比"那一节（对比 OpenCode、Claude Code、Codex 各自怎么做）就是决策痕迹。

### S5. AI 生成的代码出了 bug，你怎么定位？

**场景**：Compose 模式上线后，切换按钮"点了没反应"。代码大部分是 AI 写的，怎么排查？

**思路**：完整排查链——先怀疑前端：事件冒泡被父容器吞掉、接口失败只写控制台日志，修掉这两个问题（阻断冒泡 + 可见的失败提示）后**依然失败**。换思路：不再在前端打转，直接拿运行中服务的凭证调接口验证——健康检查返回 200，新接口返回 404，说明**运行中的服务进程里根本没有这个新路由**。根因：桌面端开发模式会复用已存在的后台服务，复用判断只看版本号，而这次迭代没改版本号——"新前端配了旧服务"。修复：引入源码指纹，启动时对后端源码算哈希传给服务记录，复用前比对，不一致拒绝复用、自动换新，并补了回归测试。

[追问]

> 这个案例的通用经验是什么？

两条：前端问题查不到根因时，**直接验证后端进程里到底有没有这个接口**（一次请求胜过半小时前端断点）；版本号粒度对不上时就用**内容指纹**——这个思路和前端构建的哈希指纹、HTTP 缓存标记是同一个道理。

### S6. 上游下个月发了大重构，你的分支怎么办？

**场景**：官方项目重写了记忆系统（你基于旧记忆做过定制），或者一次更新带来几百个提交。你的 fork 怎么跟进？

**思路**：先评估后决策，不无脑合并。第一步量化分叉——我做过真实分析：上游领先约 700 个提交、本地 107 个定制提交，直接 merge 的冲突和回归成本不可控。第二步按冲突面分类处理：上游重写的模块如果我有深度定制（比如记忆），**优先保护本地定制，参考上游的新设计选择性吸收重实现**；冲突面小的全新模块（比如文件历史快照这类独立新功能）可以低成本引入。第三步：任何吸收都走完整迭代流程（分叉分析 → 计划 → 失败测试 → 复审），不直接合并代码。

[追问]

> 为什么不干脆 rebase 到上游最新？

107 个定制提交分布在与上游同源的模块上，rebase 等于把每个定制在新基座上重演一遍，冲突会反复出现；成本高于"读上游设计、在本地重实现"，收益却差不多。工程决策看成本收益，不看姿势好不好看。

### S7. 巡检时用户突然开始提问

**场景**：心跳巡检时间到了，后台 Agent 正在扫描工作区、甚至可能正在写巡检日志，这时用户突然开始聊天提问。两个 Agent 会不会打架、抢上下文、或者互相打断？

**思路**：双通道设计，不会打架。心跳走**独立后台会话**——单独会话目录、后台优先级，结果写活动日志不进用户对话流，互不阻塞；心跳提示词明确声明"用户当前没有在跟你对话"，模型不会把巡检上下文当作用户提问。任务文件（笺）每轮心跳都会检查、由模型自主判断要不要行动；执行后重新落指纹防自激，单轮 5 分钟超时兜底。另外连接层面：网络断开只中断前台会话，后台巡检和定时任务不受影响，生命周期分离。

[追问]

> 怎么判定"用户空闲"？

不判定用户空闲——也不需要。心跳本来就在独立后台会话里跑，和用户对话是两条通道，不存在抢上下文；提示词层面声明"用户没在跟你对话"就够了。调度层做的冲突控制是另一回事：同一任务有并发锁，单轮执行有超时兜底。

> 巡检把自己写的东西当任务怎么办？

跳过自主活动目录，执行后重新比对指纹防止自我触发，5 分钟超时兜底。

### S8. 怎么证明你的改动让 Agent 变强了

**场景**：你说你的压缩、记忆、权限改动让 Agent 变强了。面试官要证据：评测怎么做的？数据怎么来的？会不会是自己给自己打分？

**思路**：第三方裁判，不自判。接公开的编程题库，**题目自带的测试命令是唯一事实来源**，评测只负责：拷贝工作区、跑准备命令、提交任务给 Agent、跑判定测试、记录指标，不自己实现判分器。判定规则三阶段退出码全零：准备命令通过、Agent 正常跑完、题目自带测试通过，任一失败即任务失败——Agent 异常退出时测试碰巧能过也不算，防假阳性。

评测系统自身的可信度也被独立复审过：子 Agent 交叉复审抓出九个边界问题并修复，代表性的三个——复用输出目录被上一轮代码污染（每任务先清空）、超时只杀外层进程留孤儿（改按进程树杀）、验收抢在 Agent 写完文件之前（改为等会话真正结束）。每次运行产出带时间戳的逐任务记录、汇总和可读报告，结果可追溯。

真实数据：公开题库 JavaScript 题，题目自带测试判定通过，109 秒，改 1 个文件——如实说这是单题轻量验收，不是榜单分数。指标分结果（通过）、效率（时长/改动文件数）两类；token 类指标预留未接。证明增量的方法是**控制变量**：一次只改一个环节，同一批任务对比通过率和耗时。
