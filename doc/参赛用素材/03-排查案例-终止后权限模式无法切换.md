# 03 排查案例：终止运行后权限模式无法切换

> 一句话版：用户点了"停止"按钮之后，权限模式下拉就失灵了——切任何档位都停留原处。用"现象矩阵"三行对照把根因锁死在终止清理链上：它把权限写入依赖的三份状态全部删光。修复对齐了系统内已有的"休眠"机制写法，同时保住"删除会话 = 真删除"的语义。

## 现象（现象矩阵）

| 场景 | 切权限模式 |
|---|---|
| Agent 运行途中切换 | ✅ 正常 |
| Agent 自然跑完后切换 | ✅ 正常 |
| **点终止按钮后**切换 | ❌ 点任何档位都停留在"完整权限" |
| 终止后随便发一条消息再切 | ✅ 又恢复正常（自愈） |

这不是新功能引入的问题——复现路径完全不涉及新特性，是**系统本身既有的缺陷**，只是用户很少在"终止后立刻切权限"这个时序上操作，所以一直没暴露。

## 原因

定位思路：三个"能切"的场景与一个"不能切"的场景，唯一差异是**终止清理链**——点停止会触发一次深度清理。顺着的清理代码核下去，问题清晰了：

终止时系统会做三连删（为了回收内存、保证状态干净）：

1. 删掉该会话的**运行时条目**（内存中的活体会话）；
2. 删掉该会话的**休眠元数据**（一份状态快照，本用于会话被"休眠"后仍能读写其设置）；
3. 清空**"当前聚焦会话"指针**。

而权限模式的**所有写入路径**，恰好每一条都依赖这三者之一：按会话路径写入要查运行时条目或休眠元数据，按焦点写入要查指针。三连删之后，任何一次切换请求都会被服务端以"会话不存在"拒绝。

**次生问题**更隐蔽：前端把这个失败**静默吞掉了**——只在控制台记了一行日志，界面上毫无反馈。于是用户视角就是"点了没反应，系统坏了"，而不是"这里报了个可以排查的错误"。发消息后自愈，是因为新消息触发会话运行时重建，三份状态回来了。

## 解决

修复的指导思想：**清理的目的是"释放资源"，不该连带"抹除身份"**。系统里其实已有正确示范——内存压力触发的"休眠"机制在卸载会话前，会先把会话状态快照进休眠元数据、保留会话指向，只卸载活体对象。把终止清理链对齐到同样的写法：

1. 卸载会话前，先将其状态（权限模式、工作模式、模型、目录、授权范围等）**快照进休眠元数据**；
2. 运行时条目照删（内存照常回收），但**休眠元数据保留**；
3. 焦点对象卸载，但**焦点指向保留**。

修复后的效果链：终止后切换权限模式 → 服务端按路径找到休眠元数据 → 写入成功并持久化 → 界面同步。发一条消息，会话从休眠元数据复活，权限延续用户所选。

两个必须守住的边界：

- **删除/关闭会话仍然是"真删除"**——休眠元数据在丢弃语义下会被再清一次，不能让已删除会话留下任何身份残片。为这条边界写了对照测试：终止后可切 ✅、删除后清光 ✅，两条都要成立。
- **前端不再静默**：切换失败从"只写控制台日志"改为浮出错误提示，杜绝同类服务端失败再次演变成"点了没反应"。

## 面试怎么讲

**30 秒版**：用户点终止后权限模式失灵。我用现象矩阵对照"运行中 / 自然结束 / 终止后"三种场景，把根因锁死在终止清理链——它把权限写入依赖的三份状态全删了。修复对齐系统已有的休眠机制：清理前留快照、保留会话指向，同时用对照测试保住"删除会话=真删除"的语义；顺带把前端静默吞错误的问题修掉。

**可能被追问**：

- **为什么不干脆终止后什么都不清理？** 清理是必要的：活体会话对象占内存，且残留状态可能造成"已停止还在跑"的错觉。要留的只是轻量的**身份与设置快照**，量级是几十个字段的配置，不是会话本体。
- **怎么确认根因的？** 现象矩阵。三个可切场景与一个不可切场景的唯一差异是终止清理链，矛盾收敛后直接读那条链的代码，立即对上。
- **为什么以前没人发现？** 触发时序刁钻：必须"终止后、发下一条消息前"这个窗口内切权限。多数用户终止后要么直接发消息（自愈），要么不切模式。
- **前端那层为什么要改？** 服务端拒绝是有理由的拒绝，前端静默等于替用户做决定。静默失败是可用性问题里性价比最低的一种：修复成本极低，观感损害极大。

## 这段经历教我的

1. **现象矩阵是性价比最高的定位工具**：把"哪些场景好、哪些场景坏"排成表，根因方向常常自己浮现，远胜于对着代码空想。
2. **清理逻辑要区分"释放资源"与"抹除身份"**：前者必须做，后者要谨慎——用户点的是"停止"，不是"抹掉这个会话的设置"。
3. **静默失败是放大器**：一个本可一眼定位的 409，被前端吞掉后变成了"系统坏了"的玄学问题。任何用户操作失败路径都应有可见反馈。
